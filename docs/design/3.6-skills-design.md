# The superpowers skills as the process

Status: **approved 2026-11-14.** A short design for a small change to the process documents and their test. No change to the script or the engine.

## Intent

Every step of Strata work names the superpowers skill the session doing it invokes, in a place every agent reads, and a test keeps the documents in agreement. The plan, the packages, the reviews and the release of 3.6 and of every later piece of work then run under the rule without a controller having to remember it.

Why now: the rule was one bullet under "Working in parallel" in AGENTS.md and a list of seven skills in `docs/workflow.md`. A worker invoked a skill only because a dispatch file said so, and that file was untracked and rewritten for each plan. The transcripts from 2026-11-12 to 2026-11-14 show what that gave: 48 of 49 code workers invoked `superpowers:test-driven-development` (one fix worker never did, and one package's worker did only on its second round), workers invoked `superpowers:systematic-debugging` three times by choice, and no session invoked `superpowers:verification-before-completion`.

## Goals

1. **AGENTS.md** has a top-level section, "How work is done: the superpowers skills", right after Project Overview: one line per step with its skill. It replaces the bullet under "Working in parallel" and stays inside the 8,000-word budget.
2. **`docs/workflow.md` (Skills)** names eleven skills, each with who invokes it and when. The four added:
   - `superpowers:dispatching-parallel-agents`: the controller, each time it sends two or more agents at once (a wave's packages, a design's fact gathering, a review split between reviewers).
   - `superpowers:systematic-debugging`: whoever meets a failing test, a failing check or behavior it did not expect, before proposing or making a fix; a bug-fix package starts with it.
   - `superpowers:receiving-code-review`: a worker resumed with a reviewer's findings, and the controller with a final review's or a pull request's findings.
   - `superpowers:verification-before-completion`: a worker before it reports a status, and the controller before it lands a batch, merges, closes an issue or calls a release done.
   It also says which roles invoke no skill of their own (a reviewer, a read-only agent gathering facts), that `superpowers:executing-plans` is not used, and that work outside a release (a batch of fixes, a docs change) runs on the same skills, with its plan in its ledger folder.
3. **A tracked dispatch text** in `docs/workflow.md` (Dispatch): the skill lines every worker's dispatch carries word for word. A subagent is told to skip the skills' own start-up instructions, so the dispatch is the only thing that makes a worker invoke one.
4. **Reports and review.** A worker's report has a "Skills" line: each skill it invoked and at which step, or why one did not apply. A reviewer requests changes on a package whose report lacks a skill its work required. A brief names the skills its package invokes, and every task of a plan carries a `**Skills:**` line.
5. **A docs test** (`test/unit/docs_test.lua`): AGENTS.md's section and the workflow's Skills name the same skills; the dispatch text names every worker skill; every `superpowers:<name>` in a maintained doc or a plan is a skill the process knows; every plan under docs/superpowers/plans/ names the execution skill and a skill for each task.
6. **The 3.6 design** (its own pull request) says in its work packages section which skills the plan, the waves, each kind of package and the release run under.

## Non-goals

- No hook and no check of transcripts: transcripts live outside the repository, so that check cannot be a test.
- No change to parallel packages, batch landings or the rebase rules, which still win over a skill.
- No skill from another plugin, and no edit to a skill.

## Anti-goals

- **A skill with no step.** A docs-only package still skips `superpowers:test-driven-development`; a known flaky check is rerun as its brief says, not debugged.
- **A test that pins wording.** The test compares skill names per section and looks for the "Skills" line; it never compares sentences.

## Approaches

1. **Docs only**: rewrite AGENTS.md and `docs/workflow.md` so every step names its skill. Cheapest, and what the process already had in a smaller form; nothing makes a worker's dispatch carry the lines, and nothing notices when the two files drift.
2. **A tracked dispatch text, a report line and a docs test** (picked): the documents, plus the three things that make the rule hold without a controller's memory. Costs one section, one report line and four tests.
3. **The same, plus a check of each worker's transcript** before its review: the only approach that proves the Skill tool was called. Declined: the transcripts are outside the repository and their format is the harness's, so the check would be a controller step that breaks silently.

## Left to the builder

- The wording of each line, within the plan's text.
- How the test reads a section and a fenced block.

## Cost if wrong

- **More invocations per worker** (verification, debugging, review findings): tokens and minutes on every package. If a skill proves to be ceremony for a kind of package, its line in Skills gets the exception, as the code skill has for docs-only packages.
- **`superpowers:dispatching-parallel-agents` overlaps the execution skill**: two skills at one step. Its trigger is narrow (two or more agents sent at once) to limit that; if it adds nothing in 3.6's waves, the line goes.
- **AGENTS.md's word budget**: the section takes about 100 of the 144 words that were free, so 3.6's packages have to make room for their rows by moving detail to notes files.
