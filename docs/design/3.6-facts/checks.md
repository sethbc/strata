# Facts for 3.6: what the sources settle

Design §0.5 left eight questions for documents and source code to settle before the device packages build on them. Each section below names its sources with their commit or version, answers from them by file and line or by URL, and ends with `Answer:`, and with `Unverified until #6:` where a doubt stays. Nothing here was tried on a device.

Answers in four sections contradict the design or the plan. Each is marked **Contradicts** in its section:
- §1: nb's voice mods register plain tables with no `count_up`, `count_down` and often no `active` or `stop_all`; nb's host supplies them. Plan 2f calls `count_up()` on the player, and plan 0d's nb stub gives every player those methods. A second nb host also needs nb's sentinel param.
- §4: iii's `device_version()` returns the device firmware's date tag (`v240324`, `v260324`), not iii's version, so design §9.4's "older than 1.1.0" check cannot compare it.
- §7: with the midigrid mod active, `grid.connect(n)` ignores `n`, and a handler assigned to `grid.add` lands on the mod's facade. This breaks Strata's grid ports 1 to 4 on `main` today, and design §0.1's guard does not cover it.
- §8: softcut clamps `pre_filter_fc` to 12000 Hz (design §12 opens at 16000), its default `pre_filter_rq` of 4 dulls every pass even with no wear, the write path's soft clipper gains 1.2 (so feedback above about 0.83 never decays), and `pre_filter_fc_mod` does not take effect until the next `pre_filter_fc` or `rate` call (plan 1f sends it after `pre_filter_fc`).

## 1. The nb host's duties

Sources: nb `400e0b38` (`lib/nb.lua`, `lib/player.lua`, `nb.lua`, `README.md`); voice mods, each `lib/mod.lua`: nb_crow `bac2a6d` (2023-02-05), nb_jf `fc0922f` (2024-04-12), nb_ex `ac7c134` (2023-02-05), nb_drumcrow `892ee53` (2024-10-17), nbout `610818c` (2023-10-15), nbin `867007e` (2024-06-19), nb_midiconfig `6a8b044` (2024-09-10); norns `lua/core/script.lua`, `lua/core/paramset.lua`.

**When players exist.** norns runs the script file, then the `script_pre_init` hooks, then `init()` (`script.lua:215`, `:231-241`, `:145-150`). Every listed mod fills `note_players` in its `script_pre_init` hook (nb_crow `:304-308`, nb_jf `:363-371`, nb_ex `:45-47`, nb_drumcrow `:681`, nb_midiconfig `:515`), so the table is empty while Strata's modules are included and full at `init()`. `Script.clear` gives each script a fresh global table (`script.lua:40-50`, the metatable at `:43`), so `note_players` and `nb_player_refcounts` never survive a script change.

**How a mod registers.** Each mod does `if note_players == nil then note_players = {} end` and then `note_players[name] = player`, where `player` is a plain table with its own methods and no metatable (nb_crow `:8-10`, `:18-133`; nb_jf `:6-8`, `:53`, `:145`; nb_ex `:4-6`, `:42`; nb_drumcrow `:578-581`; nb_midiconfig `:162-163`, `:506`). No mod defines `count_up` or `count_down`. Which other methods each defines varies:
- nb_crow's two mono players (`crow 1/2`, `crow 3/4`): `active`, `inactive`, no `stop_all` (`:18-133`); its `crow para`: `active`, `inactive`, `stop_all` (`:257-269`).
- nb_jf: `stop_all` and `delayed_active` (which sends `crow.ii.jf.mode(1)`, or `mode(0)` for the kit); no `active`; `inactive` on the mono and unison players only, written to clear `is_active` and cancel `active_routine`, fields that only nb's default `active` sets (`:45-51`, `:126-143`, `:186-200`, `:282-288`, `:352-358`).
- nb_ex: `stop_all` (empty) only; no `active` or `inactive` (`:8-43`).
- nb_drumcrow: `active` and `inactive`, which do nothing unless `self.name` is set (`:491-503`), `stop_all` (empty).

**What nb's own host does for a player** (`lib/nb.lua`, `lib/player.lua`):
- `nb:get_player` wraps the mod's table with `player_lib:new(nb.players[name])` (`nb.lua:148`), which sets the table's metatable so every method the mod left out falls back to nb's base player (`player.lua:11-16`), then sets `ret.name = name` (`nb.lua:149`) and calls `ret:count_up()` (`:151`). The base supplies: `count_up` and `count_down` (`player.lua:126-148`), `active` (`:86-95`: sets `is_active`, starts a clock that sleeps 1 s and calls `delayed_active` if still active), `delayed_active` and `inactive` (`:99-109`, `inactive` clears `is_active` and cancels that clock), and empty `stop_all`, `note_on`, `note_off`, `add_params`, `pitch_bend`, `modulate`, `modulate_note`, `set_slew`, `describe` (`:19-82`, `:112-113`).
- The refcount is the global `nb_player_refcounts[name]`, created by `player.lua:5-7` and reset to `{}` by `nb:init` (`nb.lua:112`). `count_up` calls `active()` when a name's count goes from none to 1; `count_down` calls `inactive()` when it returns to 0; both do nothing when `name` is nil (`player.lua:126-148`).
- `nb:init` (`nb.lua:111-115`): resets the refcounts, adds a `midi: <name> <j>` player for each connected MIDI vport (`:25-108`), and calls `stop_all` on every player.
- `nb:add_param(id, name)` (`nb.lua:120-174`): an option param of `none` then the players' names sorted (`:121-128`); a text param `<id>_hidden_string`, hidden (`:129-131`); `get_player` reads the text param and counts the old player down and the new one up only when the name changes (`:134-154`); the text param's action selects the matching option silently and calls `get_player` (`:161-168`); the option param's action writes the name to the text param, but only once the param is initialized (`:169-173`), which a clock does 1 s after `add_param` by calling `get_player` (`:156-160`). So the text param is what a PSET restores, and a PSET or bang in the first second cannot overwrite it from a stale option index.
- `nb:add_player_params()` (`nb.lua:192-201`): returns at once if the param `nb_sentinel_param` exists; otherwise calls every player's `add_params()` in name order, then adds `nb_sentinel_param` as a hidden binary param.
- `nb:stop_all()` calls `stop_all` on every player; its comment says to call it at a PSET load (`nb.lua:213-218`).
- nb defines no cleanup, and `player.lua` defines no cleanup method. `describe()` has no `stop_all` field (`player.lua:72-82`; the key `voice_mod_tarets` is misspelled in the source).
- The include line: nb's README gives none; nb's example script uses `require "nb/lib/nb"` (`nb.lua:1`), and nbout uses `require('nbout/lib/nb/lib/nb')` (nbout `:2`). Strata loads no nb file, so it needs neither.

**Other hosts in the same session.** nbout and nbin are hosts too, with nb vendored in their own folders. nbout replaces the global `midi` with a facade whose `vports` has an extra entry and calls `nb:init` in `script_pre_init` (nbout `:86-139`), then in `script_post_init` calls `nb:add_param` and `nb:add_player_params` (`:141-146`). nbin calls `nb:init` in `script_post_init` (nbin `:119-122`), which resets `nb_player_refcounts` after Strata's `init` has counted its players up, and sets a MIDI vport's `event` itself (`:95-117`, its `midi_device[i]` being `midi.connect(i)`). If Strata adds the players' params without nb's sentinel, nbout's `add_player_params` adds them all again, and norns then prints an ID collision for each and overwrites the param (`paramset.lua:151-160`).

**Which listed mods send to crow or ii themselves:**
- nb_crow: crow's outputs through the proxy (`crow.output[n].volts`, `.action = "<asl>"`, `crow.output[n]()`), outputs 1 to 4 (`:59-63`, `:71-72`, `:83-84`, `:178`, `:217`, `:243`, `:258`). No ii.
- nb_jf: ii to Just Friends through crow (`crow.ii.jf.*`, `:18-357`), so crow leads the bus.
- nb_ex: ii to a Disting EX through crow (`crow.ii.disting.*`, `:16-27`).
- nb_drumcrow: drives crow's four outputs through functions of a script it uploads to crow, line by line with `norns.crow.send` between `^^s` and `^^e` (`:455-485`), at `script_post_init` when its "upload script start" setting is on (default off, `:664-680`); that upload replaces whatever crow was running. It also sends `crow.ii.crow[1].call4(...)` to a second crow for voices 5 to 8 (`:539`).
- nbout, nbin, nb_midiconfig: MIDI only, no crow or ii.

**Contradicts** plan 2f and plan 0d. 2f's Produces says "A chosen player gets `count_up()` and a deselected one `count_down()`" and calls `player:stop_all()`; on a real mod's player those calls raise (no `count_up` on any mod, no `stop_all` on nb_crow's mono players), and without nb's default `active`, nb_jf's players never reach `delayed_active` and never switch Just Friends' mode. 0d's nb stub gives every player `count_up`, `count_down`, `active`, `inactive` and `stop_all`, so 2f's tests would pass against players no mod writes. Design §7's list also lacks the sentinel. What a host must do instead, from the above, written in Strata's own code (nb declares no license, so none of its code is copied):
1. At init, read `note_players` (nil or empty: the list is `none`); set each chosen player's `name` to its key.
2. Keep the refcount in the global `nb_player_refcounts[name]` (create it when nil, never reset it, so other hosts agree); on a count from none to 1 call the player's `active` if it has one, else do the base's: set `is_active` and, after 1 s, call `delayed_active` if it exists and the player is still active; on a count back to 0 call `inactive` if it exists, else clear `is_active` and cancel that clock.
3. Call `note_on`, `note_off` and `stop_all` only when the player has them.
4. Unless `params.lookup["nb_sentinel_param"]` exists, call each player's `add_params` (when present) in name order, then add the hidden binary `nb_sentinel_param`.
5. Keep the chosen name in a hidden text param, as nb does, and select from it on a PSET load; nb also calls `stop_all` at a PSET load.

Answer: a voice mod puts a plain table in the global `note_players` during `script_pre_init`; nb's host, not the mod, supplies the refcount (`count_up`, `count_down` on the global `nb_player_refcounts`), the name, the default `active` with its one-second `delayed_active`, and empty defaults for every other method, and adds each player's params once behind `nb_sentinel_param`; a hidden text param holds the chosen name. A player needs nothing at cleanup beyond `stop_all`. nb_crow (crow outputs), nb_jf and nb_ex (ii through crow) and nb_drumcrow (its own crow script, and ii to a second crow) send to crow or ii themselves.

Unverified until #6: what each mod does on a device when its `active` or `delayed_active` runs late or twice (only the code was read); whether nbout's replaced `midi` global, present for the whole session, changes what Strata's MIDI ports see (`midi.vports` gains an entry).

## 2. The E16's 14-bit pairing and script indexes

Source: OXI E16 User Manual 1.0.1a (title page: "Official User Manual 1.0.1a"; change log entry "1.0.1 a", July 2026), text extracted with `pdftotext -layout`. Pages are the manual's printed numbers (PDF page = printed page + 8).

**14-bit pairing.** The manual's CC14 table (page 24, "CC 14 (High Res) - Control Change Absolute - High Resolution") sets the two CC numbers separately: "MSB, Most Significant Byte: Coarse adjustment. CC number used for the MSB message destination. Typically this uses CC 0-31, but check with the destination device to pair correctly", and "LSB, Least Significant Byte: Fine adjustment. CC number used for the LSB message destination. Typically this uses CC 32-63". The type sends "absolute CC values over a range of 0-16,383 ... using MSB and LSB messaging to the CC numbers" (page 24). NRPN works "in a similar way with an MSB / LSB messaging approach" (page 29). The manual does not say in which order the two messages go out. Internally "The E16 stores all values internally as 14-bit integers (0–16383)" (section 6.1, page 86). Strata's design reads the E16 only as relative CCs (design §8.1), so nothing builds on this pairing.

**Script indexes.** Section 6.1, page 86: "All indices in the Lua API are 1-based (encoder 1–16, page 1–12). The firmware converts internally." Section 6.8, page 97: `leds.update(index, value [, color])`, "index: Encoder position (1–16)", "value: Ring fill amount (0–16383, where 16383 = full ring)", "color: Color index (0–15, optional, defaults to 0)"; once called, the firmware stops drawing that ring until `leds.reset(index)`. Section 6.9, page 98: `slots.update(index, text)`, "index: Encoder position (1–16)", "text: Label text (max 4 characters displayed)". Section 6.11, page 102: `page.setTitle(text)`, "Max 15 characters". `controller.onSysex(bytes)` gets "a table of raw byte values (integers), including the 0xF0 and 0xF7 framing bytes", and the manual's example reads the manufacturer byte as `bytes[2]` (page 92), so `bytes[1]` is `0xF0`. Page 92 also says overlays "are not automatically cleared on page change — your script manages this".

So Strata's frames, whose index byte runs 0 to 15 (design §8.1, plan 1c), need the E16 script to call `leds.update(index + 1, ...)` and `slots.update(index + 1, ...)`, and the ring frame's sixteen values go to encoders 1 to 16 in order.

Answer: the E16's CC14 type sends an MSB on one CC and an LSB on another, each set by the user (typically 0-31 and 32-63, so n and n + 32 by convention only); `leds.update` and `slots.update` count encoders from 1 to 16, and the script must add 1 to Strata's 0-based index byte.

Unverified until #6: the order of the MSB and LSB messages; whether rings and labels drawn by a script stay visible on the page a relative-type control is on.

## 3. The E16's rel2 direction

Source: the E16 manual 1.0.1a, page 23 (printed numbering; PDF page 31), "NOTES CC Rel 1 & 2 - Control Change Relative".

The manual's sentence: "Relative 1 will send a value of 1to increment the control and 127 to decrement. Relative 2 operates the same but uses 63 to increment and 65 to decrement the destination." The type list names them "CC Rel1" and "CC Rel2" (pages 22-29). The manual gives no value other than these four, so it implies one message per detent; the encoder Mode setting (Div, Acc, LSp) is listed in the CC Abs and CC14 tables (pages 22 and 24), not in the CC Rel table (page 23).

This agrees with design §8.1 and plan 1c: under rel2, 63 is one step up and 65 one step down.

Answer: 63 is up and 65 is down ("Relative 2 ... uses 63 to increment and 65 to decrement"); rel1 sends 1 up and 127 down.

Unverified until #6: whether a fast turn ever sends a larger step (2, 62, 126) in either relative type.

## 4. iii's LED range and USB name

Sources: iii `ed920efa` (`iii.h:1` `III_VERSION "v1.1.2"`, `vm.c`, `lua/lib.lua`, `changelog.md`, `tusb_config.h`); iii-grid-one `2724b6da`, iii-grid-zero `8f369760`, iii-grid-2022 `8e0a4121`, iii-arc `8b8f67cf` (each `main.c` and `usb_descriptors.c`); norns `matron/src/device/device_monitor.cc` and `device_midi.cc`.

**LED range.** `grid_led(x, y, z, rel)` takes x and y from 1, ignores a cell outside the grid, and clamps z to 0..15 (with `rel`, the sum with the current level is clamped) (iii-grid-one `main.c:317-328`; the same in grid-2022 `:345-356` and grid-zero `:359-370`). `grid_led_all(z, rel)` clamps the same way (`main.c:339-358`). `arc_led(n, x, z, rel)` takes ring n 1..4 and LED x 1..64, ignores anything outside, and clamps z to 0..15 (iii-arc `main.c:468-483`); `arc_led_ring` and `arc_led_all` clamp the same way (`:495-535`). `grid_refresh()` only marks the grid due (`main.c:368-372`).

**Grid sizes.** iii-grid-one and iii-grid-2022 are 16 by 8 (`#define GRID_X 16`, `GRID_Y 8`: grid-one `main.c:85-86`, grid-2022 `:82-83`); iii-grid-zero is 16 by 16 (`:82-83`). No iii firmware is 8 by 8 or 8 by 16.

**Callbacks.** `event_grid(x, y, z)` gets x and y from 1 (grid-one `main.c:416-426`); `event_arc(n, d)` gets n from 1 (iii-arc `main.c:586-592`); `event_arc_key(z)` takes one argument (iii-arc `main.c:595-602`, and its help text `:568-569`), which settles the code page's `(n,d)` misprint.

**USB name.** The USB product string comes from `device_str2()`, not from the table's `"iii"` entry (`usb_descriptors.c:186-192` in each device repository). In iii mode it is `"iii grid"` on the grids and `"iii arc"` on the arc; in monome serial mode it is `"grid"` or `"arc"` (grid-one `main.c:499-501`, iii-arc `main.c:693-695`; mode 0 is iii, `main.c:62-68`). The manufacturer string is `"monome"` (`main.c:495-497`). In iii mode the device exposes one CDC serial interface and one MIDI interface with one cable (`usb_descriptors.c:110-120`, `tusb_config.h:93`, `:96`). norns names a MIDI device by its USB `product` attribute (`device_monitor.cc:312-316`, `:348-361`) and appends a port number only to a device with several ports (`device_midi.cc:89-99`), so a host sees `iii grid` or `iii arc`; two such devices show the same name on different ports. The CDC tty is not taken for a monome device, since its model is not `grid`, `arc` or `monome…` (`device_monitor.cc:364-394`); norns reports it as an unmatched serial device (`:280-296`).

**Versions.** `device_version()` returns the device firmware's own tag, `DEVICE_VERSION`: `"v240324"` on grid one, `"v260324"` on grid zero, grid 2022 and arc (each `main.c:1` and `device_version()`: grid-one `:491-493`, iii-arc `:685-687`). iii's own version is the global string `iii_version`, set by the first line of `lib.lua` (`lua/lib.lua:1`, `iii_version="v1.1.2"`; added in v1.1.1, `changelog.md:3-5`). `device_version()` itself is new in v1.1.0 (`changelog.md:46`), as are `event_grid`, `event_arc`, `event_arc_key` and `event_midi`.

**Contradicts** design §9.4 ("Each checks `device_version()` and shows a fixed pattern on a firmware older than 1.1.0") and plan 1d ("reads `device_version` ... and, below 1.1.0, shows a fixed pattern"): `device_version()` returns a date tag such as `v240324`, which no comparison with 1.1.0 can read. A device script can tell iii 1.1.0 or later by `type(device_version) == "function"` (or by `iii_version`, from 1.1.1). Plan 1d's `REMOTE.sizes` also lists 8 by 16 and 8 by 8, which no iii grid reports (harmless, since they only widen what is accepted).

Answer: `grid_led` and `arc_led` take levels 0 to 15 (clamped, 1-based coordinates); a host sees the MIDI device as `iii grid` or `iii arc`; iii grids are 16 by 8 or 16 by 16.

Unverified until #6: the name as norns actually lists it (udev's `product` attribute was read from source, not observed); whether two devices with the same name keep their ports across a restart.

## 5. The .tosc schema

Sources: tosclib 0.3.5 at `ac0fb2cf` (`src/tosclib/tosc.py`, `controls.py`, `elements.py`) and two layouts in its repository, `tests/test_layout.tosc` and `docs/demos/files/stoic.tosc`, decompressed and read. Hexler publishes no schema (the manual describes the editor only), so this is the format as the library and those files show it. stoic.tosc lists every property of each control in alphabetical order, as the editor writes them, but its provenance is not stated.

**The file.** A `.tosc` file is the UTF-8 XML document compressed with zlib (with the zlib header): `tosc.py:430-441` (`zlib.decompress` to load, `zlib.compress(ET.tostring(root, encoding="UTF-8"))` to write); both sample files decompress with Python's `zlib.decompress`. The root is `<lexml version="3">` holding one `<node type="GROUP">`, the whole layout (`tosc.py:409-419`).

**A node.** Every control is `<node ID="<uuid4>" type="<TYPE>">` with, in order, `<properties>`, `<values>`, `<messages>` and, for a group, `<children>` (`controls.py:518-543`). Types: `BOX`, `BUTTON`, `LABEL`, `TEXT`, `FADER`, `XY`, `RADIAL`, `ENCODER`, `RADAR`, `RADIO`, `GROUP`, `PAGER`, `GRID` (`elements.py:39-55`).

**Properties.** Each is `<property type="T"><key>name</key><value>…</value></property>`, `T` one of `s` string, `b` boolean (`0`/`1`), `i` integer, `f` float, `r` frame, `c` color (`elements.py:58-66`, `controls.py:550-569`). A frame's value holds `<x>`, `<y>`, `<w>`, `<h>`; a color's `<r>`, `<g>`, `<b>`, `<a>` from 0 to 1. Every control has `name`, `frame`, `color`, `locked`, `visible`, `interactive`, `background`, `outline`, `outlineStyle`, `grabFocus`, `pointerPriority`, `cornerRadius`, `orientation` (`controls.py:33-60`, and stoic.tosc's top group).

**Values.** Each is `<value><key>x</key><locked>0</locked><lockedDefaultCurrent>0</lockedDefaultCurrent><default>0</default><defaultPull>0</defaultPull></value>` (`elements.py:157-182`, `controls.py:592-597`). A fader and a button have `touch` (default `false`) and `x`; a label has `text`, whose `<default>` is the text shown, and `touch` (stoic.tosc).

**Pages.** A `PAGER` node's children are `GROUP` nodes, one a page, each with the extra properties `tabLabel` (string), `tabColorOff`, `tabColorOn`, `textColorOff`, `textColorOn` (`controls.py:263-270`; stoic.tosc's page "Monitor"). The pager has `tabLabels`, `tabbar`, `tabbarDoubleTap`, `tabbarSize`, `textSizeOff`, `textSizeOn` (`controls.py:248-260`).

**Per control** (from `controls.py:146-172` and the nodes of stoic.tosc): a fader adds `response` (0 absolute, 1 relative), `responseFactor`, `grid`, `gridSteps`, `cursor`, `cursorDisplay`, `bar`, `barDisplay`; a button adds `buttonType` (0 momentary, 1 toggle on release, 2 toggle on press), `press`, `release`, `valuePosition`, `shape`; a label adds `font`, `textSize`, `textColor`, `textAlignH` (1 left, 2 center, 3 right), `textAlignV`, `textLength` (0 unlimited), `textClip`.

**An OSC message** (in `<messages>`; `elements.py:185-333`, `controls.py:607-622`; the structure of stoic.tosc's fader `peak`, with its four path partials replaced by one constant and `send` set to 1):

```xml
<osc>
  <enabled>1</enabled><send>1</send><receive>1</receive><feedback>0</feedback>
  <connections>00001</connections>
  <triggers><trigger><var>x</var><condition>ANY</condition></trigger></triggers>
  <path>
    <partial><type>CONSTANT</type><conversion>STRING</conversion><value>/param/macro_1</value><scaleMin>0</scaleMin><scaleMax>1</scaleMax></partial>
  </path>
  <arguments>
    <partial><type>VALUE</type><conversion>FLOAT</conversion><value>x</value><scaleMin>0</scaleMin><scaleMax>1</scaleMax></partial>
  </arguments>
</osc>
```

`connections` is a five-character bit string, the last character connection 1 (`00001` is connection 1, `00011` connections 1 and 2; `elements.py:291-292`, and all three forms appear in stoic.tosc). A trigger's `var` is the value it watches (`x`, `touch`, `text`) and its `condition` `ANY`, `RISE` or `FALL` (`elements.py:215-228`); stoic.tosc uses `touch` with `RISE` on 29 messages. A partial's `type` is `CONSTANT`, `INDEX`, `VALUE` or `PROPERTY`, its `conversion` `BOOLEAN`, `INTEGER`, `FLOAT` or `STRING`, and `scaleMin` and `scaleMax` scale a `VALUE` (`elements.py:185-212`). A path is the concatenation of its partials (stoic.tosc builds `/<parent.name>/<name>` from `CONSTANT "/"` and `PROPERTY "name"` partials; one `CONSTANT` partial with the whole address is the simplest form). A fixed argument is a `CONSTANT` partial, for example `<type>CONSTANT</type><conversion>INTEGER</conversion><value>3</value>` for `/strata/scene 3` (stoic.tosc has `CONSTANT` arguments as `FLOAT` and `STRING`).

Answer: a `.tosc` is zlib-compressed XML, `<lexml version="3">` around one root `GROUP` node; pages are `GROUP` children of a `PAGER`; every node is `<node ID type>` with `properties` (typed key and value), `values` (key, locked, lockedDefaultCurrent, default, defaultPull) and `messages`, whose `<osc>` holds the flags, `connections`, `triggers` and `path` and `arguments` as lists of partials, as shown above.

## 7. midigrid's connect

Sources: midigrid `beb75e82` (`lib/mod.lua`, `lib/midigrid.lua`, `lib/vgrid.lua`, `lib/mg_128.lua`); norns `lua/core/grid.lua`, `lua/core/midi.lua`, `lua/core/startup.lua`; Strata `lib/grid/core.lua` on `main` (`022f80af`).

**The mod replaces the global `grid`.** At `system_post_startup` the mod sets `grid = fake_grid` (`mod.lua:314-356`), a table whose metatable sends every missing key to the real grid module (`mod.lua:84-100`) and which defines no `__newindex`. So reading `grid.vports`, `grid.devices`, `grid.cleanup` reaches the real module, but assigning `grid.add = f` or `grid.remove = f` writes a field of the facade, and norns' hot-plug calls the real module's `Grid.add` (`grid.lua:198`), never the facade's.

**The replacement `grid.connect(idx)`** (`mod.lua:110-140`):
- With the mod's "midigrid active" setting on (the default, `mod.lua:66`): whatever `idx` is, it runs `include "midigrid/lib/midigrid"`, which `dofile`s a fresh copy of the library each call (`startup.lua:52-65`), calls its `init` with the mod's size, rotations, palette and places, and returns `midigrid.connect(idx)`; "if midigrid is active we rather rudely provide midigrid no matter what index was requested" (`mod.lua:118-131`).
- `midigrid.connect` ignores its argument (`midigrid.lua:61`). With no supported MIDI device it returns `midigrid.core_grid.connect()` with no argument (`midigrid.lua:91-100`), which is the real `Grid.connect(nil)`, that is `grid.vports[1]` (`grid.lua:137-141`). With a supported device it returns the midigrid table: functions `led`, `all`, `refresh`, `intensity` and `rotation` (the last two do nothing), numbers `cols` and `rows` (16 and 8 for the mod's default size 128), `device = {id = 999, cols, rows, name = "midigrid", serial = 1234567}`, `name = "Midi Grid"` and `vports = {midigrid}`; the script sets its `key` (`midigrid.lua:17-35`, `:105-116`, `:290-313`, `vgrid.lua` `vgrid.key`).
- With the setting off: the real `grid.connect(idx)` (`mod.lua:137-139`). Without the mod: the real grid module.

**When it wraps `midi.add` and `midi.remove`.** Only in a `connect` that found a supported device: after attaching the devices it calls `setup_connect_handling` (`midigrid.lua:118-119`), which saves the current `midi.add` and `midi.remove` and installs its own (`:244-249`); its add calls the saved one with the same arguments (`:251-254`), and its remove first runs the departing device's `_cleanup` (restoring a send it patched), then calls the saved one (`:256-268`). A `connect` that found nothing wraps nothing. Every such `connect` wraps again, so each repeated call adds one more link to the chain, and each re-attaches the devices with a fresh copy of the library. norns' `midi.cleanup` at a script change puts back empty `midi.add` and `midi.remove` and clears every device's `event` (`midi.lua:198-209`). midigrid sets each Launchpad's `midi.devices[id].event` (`vgrid.lua:107`); norns still calls the port's vport `event` after the device's (`midi.lua:461-475`), so a listener on that vport also receives the pads' notes. This corrects controllers.md §5, which says the device cannot be used as a MIDI controller at the same time: both receive every message.

**Contradicts** design §0.1 and §9.5 as plan 0a and 1d build them, and Strata's grid code on `main`. Strata's `grid_init`, `reconcile_ports` and `attach_grid` call `grid.connect(port)` for ports 1 to 4 (`lib/grid/core.lua:610-619`, `:662-669`, `:707-709`), and its hot-plug handlers are assigned as `function grid.add` and `function grid.remove` (`:676`, `:686`). With the mod active today: with a Launchpad, each of those calls (two a port at init) loads a fresh copy of midigrid that attaches the Launchpad again and wraps `midi.add` again, a different copy is attached at each of the four ports, the Launchpad's keys reach only the copy attached last (port 4), and a monome grid is never attached; without one, `grid.vports[1]` is attached at all four ports (its `key` set four times, the last to port 4); in both cases monome grids plugged in later never reach Strata's `grid.add`. Design §0.1's guard ("what `grid.connect(port)` returns is attached only when it is `grid.vports[port]`") stops the duplicates, but a monome grid on port 2, 3 or 4 is still never attached (each `grid.connect` returns `vports[1]` or midigrid), each of the four calls still re-includes midigrid and wraps `midi.add` again, and hot-plug still misses. Reading `grid.vports[port]` directly for ports 1 to 4 (the facade passes `vports` through) avoids the first two; the third needs the handlers on the real module, which the mod keeps as `grid.real_grid`. Plan 1d's `rescan` calling `grid.connect()` again adds a link to the `midi.add` chain and a fresh library copy each time.

Answer: with the mod active, the replacement `grid.connect` returns the same thing for every port argument: the midigrid object when a supported MIDI grid is connected, otherwise `grid.vports[1]` (from `connect()` without an argument); it wraps `midi.add` and `midi.remove` only in a `connect` that found a device, again at every such call. With the setting off, or without the mod, `grid.connect(n)` is norns' own.

## 8. softcut's write path

Sources: norns `227aa044`: `crone/src/SoftcutClient.cpp`, `SoftcutClient.h`, `crone.cpp`, `MixerClient.cpp`, `Commands.cpp`, `Commands.h`, `matron/src/weaver.cc`, `lua/core/softcut.lua`, `lua/core/script.lua`, `lua/core/state.lua`; softcut-lib `ce870c55` (the submodule norns pins): `softcut-lib/src/Voice.cpp`, `SubHead.cpp`, `ReadWriteHead.cpp`, `FadeCurves.cpp`, `Svf.cpp`, `include/softcut/SoftClip.h`, `Softcut.h`.

**The path, one audio block.** crone's `process` handles queued commands, clears the input buses, mixes each recording voice's input, runs each enabled voice, then mixes the outputs (`SoftcutClient.cpp:49-61`). `mixInput` gives a voice `dst` that is recording and enabled the two input channels at `inLevel[ch][dst]` and every playing, enabled voice's output at `fbLevel[src][dst]` (`:75-88`). The output buses are not cleared (`:68-73`), so a voice's own output enters its input one block later. `level_cut_cut(src, dst, amp)` sets `fbLevel[src - 1][dst - 1]` and `level_input_cut(ch, voice, amp)` sets `inLevel[ch - 1][voice - 1]` (`weaver.cc:3199-3206`, `:3370-3377`; `SoftcutClient.cpp:119-126`). Each voice is mono (`SoftcutClient.h:44-45`). The two input channels are the mixer's softcut sink: the ADC at the system's `cut_input_adc` level (0 dB by default, `state.lua:44`), the engine at `level_eng_cut`, and tape playback (`MixerClient.cpp:91-95`).

In the voice, every input sample goes through the pre filter before anything is written: `x = svfPre.getNextSample(in[i]) + in[i]*svfPreDryLevel`, then the read and write heads run on `x`, then `out[i] = svfPost.getNextSample(y) + y*svfPostDryLevel` (`Voice.cpp:85-92`). The write: the resampled input is soft-clipped, then `buf *= preFade; buf += y * recFade` (`SubHead.cpp:99-130`), for each of the two subheads (`ReadWriteHead.cpp:32-52`). `preFade = pre + (1 - pre) * preFadeCurve(fade)`: the full `pre_level` while a subhead is fully active, rising toward 1 over the first eighth of a crossfade (`SubHead.cpp:110`; `FadeCurves.cpp:18-25`, `:82-117`).

So with `pre_level` 0, each pass erases what was there, except a short stretch at each loop crossfade where the old audio is partly kept unfiltered, and writes the new input, which holds the voice's own previous pass through `level_cut_cut`, after the pre filter. Every pass that returns this way goes through the pre filter again, as design §12 needs. With `pre_level` above 0, the kept part (`buf *= pre`) is never filtered; only new input is.

**The post filter at defaults.** softcut-lib's `Voice::reset` sets every post filter mix to 0 and the post filter's dry level to 1 (`Voice.cpp:34-41`), and a voice passes `y * svfPostDryLevel` (`:92`). Every script load resets the voices: `script.lua:89` `softcut.reset()` → `_norns.cut_reset()` → `crone_cut_reset` (`crone.cpp:103-111`) → `SoftcutClient::reset` → `cut.reset()` → `Voice::reset` for each voice (`SoftcutClient.cpp:248-275`, `Softcut.h:23-27`). `softcut.lua`'s `defaults()` lists `post_filter_dry = 0` (`softcut.lua:460`), but that table is "synchronized by hand" (`:415`) and disagrees with the C++ here (as it does on `fade_time` 0.0005 against 0.01 at `Voice.cpp:47`). So a voice at softcut's defaults passes sound through the post filter's dry path and needs no `post_filter_dry` call; sending `post_filter_dry(v, 1)` and the four post mixes at 0 changes nothing on the device and makes the state explicit and testable.

**Four more things the C++ does** that bear on plan 1f:
1. **The cutoff is clamped to 12000 Hz.** crone clamps `pre_filter_fc` to 10..12000 (`SoftcutClient.cpp:167-170`; `softcut.lua:508`'s spec is also 10 to 12000), so the design's open cutoff of 16000 Hz is 12000, and `cutoff = 16000 * (800 / 16000) ^ wear` stays at 12000 for every wear below about 0.096.
2. **The default filter damping dulls every pass.** `Voice::reset` sets `pre_filter_rq` to 4.0 (`Voice.cpp:29`). The filter is a state-variable filter whose `rq` is its damping k (`Svf.cpp:64-69`, `:79-92`: `hp = v0 - rq * v1 - v2`), so its lowpass is 1 / (s² + k s + 1): at the cutoff it passes 1/k (-12 dB for k = 4), and it is 3 dB down at about 0.27 of the cutoff, about 3.2 kHz at 12000 Hz. Each pass compounds this, so even wear 0 loses the highs quickly. A damping of √2 (Butterworth) puts the -3 dB point at the cutoff; plan 1f sets no `pre_filter_rq`.
3. **The write gains 1.2.** The soft clipper on the write path multiplies by `g = 1.2` below its knee at 0.68 and saturates near 1.0 above it (`SoftClip.h:39-60`; `SubHead.cpp:119-121`). The fed-back pass is written at `feedback × 1.2 × |H(f)|` of what was read, so at low frequencies, where the lowpass passes 1, a feedback above 1 / 1.2 ≈ 0.83 never decays and the loop rises until the clipper holds it. Plan 1f's `tapeloop_feedback` runs 0 to 1.
4. **`pre_filter_fc_mod` takes effect only at the next `pre_filter_fc` or `rate` call.** `setPreFilterFcMod` stores the amount and does not recompute the cutoff (`Voice.cpp:214-216`); `setPreFilterFc` and `setRate` do (`:119-122`, `:185-188`, `:218-222`), with `fc = base + mod * (min(base, base * |rate|) - base)`, where the rate is the head's present rate, not the target (`ReadWriteHead.cpp:240-242`). At reset the amount is 1 (`Voice.cpp:31`). Plan 1f sends `pre_filter_fc(v, cutoff)` and then `pre_filter_fc_mod(v, 0)`; at a rate other than ±1 the cutoff stays scaled by the rate until the next `pre_filter_fc` or `rate` call. Sending `pre_filter_fc_mod(v, 0)` first avoids it. Commands reach the audio thread in the order sent (one FIFO queue of 2048, `Commands.h:17`, `Commands.cpp:40-60`).

Two smaller facts: the fed-back audio arrives one block late and is written 8 samples behind the read head (`SubHead.cpp:24`, `:164`), so each pass lands one block less 8 samples later than it was read; and the ADC goes into the loop beside Strata's output unless the system's `cut_input_adc` is turned down, since `level_input_cut` cannot tell the two apart (`MixerClient.cpp:91-95`).

**What a stereo feedback loop whose every pass goes through the filter needs**, for voice v of 1 and 2 on buffer v: `buffer(v, v)`; `level_input_cut(v, v, 1)` (input channel v into voice v; and `level_input_cut(3 - v, v, 0)`, already 0 after reset); `level_cut_cut(v, v, feedback)` (its own output back in; feedback below 1 / 1.2 if the loop must decay); `pre_level(v, 0)` (nothing kept unfiltered); `rec_level(v, 1)`; `pre_filter_fc_mod(v, 0)` before `pre_filter_fc(v, cutoff)`, with `cutoff` at most 12000; `pre_filter_lp(v, 1)` and `pre_filter_dry(v, 0)` (both reset values); a `pre_filter_rq(v, …)` chosen for the sound; the post filter left at its reset state (dry 1, mixes 0) or sent explicitly as `post_filter_dry(v, 1)`; `rec(v, 1)`, `play(v, 1)`, `enable(v, 1)` (`mixInput` feeds back only while the destination records and the source plays, `SoftcutClient.cpp:77-83`); and `audio.level_eng_cut(1)`.

**Contradicts** design §12 ("wear lowers the filter's cutoff from 16000 Hz to 800 Hz") and plan 1f (`TAPE.cutoff_open = 16000`, the On sequence's order of `pre_filter_fc` then `pre_filter_fc_mod`, no `pre_filter_rq`, `tapeloop_feedback` up to 1): the cutoff cannot exceed 12000 Hz; the default damping leaves wear 0 far from open; feedback above about 0.83 does not decay; and the `fc_mod` call must come first. The design's central claim holds: with `pre_level` 0 and the voice's output fed back through `level_cut_cut`, every pass is filtered.

Answer: yes, a voice's own output fed back through `level_cut_cut` passes the pre filter on every pass, because the filter sits on the voice's whole input before the write (`Voice.cpp:87`), while `pre_level` scales the old audio in the buffer, which never passes the filter (`SubHead.cpp:125-126`); at softcut's defaults a voice passes sound through the post filter's dry path (dry 1 after every reset, `Voice.cpp:41`), so `post_filter_dry` need not be set, though setting it to 1 is harmless; the loop needs the calls listed above, with the cutoff at most 12000 Hz, a chosen `pre_filter_rq`, `pre_filter_fc_mod` sent before `pre_filter_fc`, and feedback under about 0.83 for a loop that decays.

Unverified until #6: how the loop sounds at each wear and feedback (the arithmetic above is from the code, not heard); the audio block size, which sets how far each pass shifts.
