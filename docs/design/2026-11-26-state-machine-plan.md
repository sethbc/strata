# State-machine audit implementation plan

Archived November 26, 2026 plan for the findings reproduced on v3.9.0 (`d8621dd5`). The checkboxes preserve the original acceptance criteria. The dated audit records what landed and links to the remaining device checks.

**Goal:** Keep the bytes, held notes, devices and transports in the state the player requested, including after a reload, dropped notification or lost release.

**Architecture:** Keep ownership in the existing modules. Use the existing transition tables for compound protocols, a derived reader for views, and an identity for work that survives a callback. Store applied configurations only where Strata must remember which owner received an earlier event.

**Tech stack:** norns Lua and LuaJIT, SuperCollider 3.13 and 3.14.1, the existing unit harness, scsynth check areas and hardware check #6.

The findings, fixtures and subsequent work are in the [dated audit and evidence index](2026-11-26-state-machine-audit.md).

## Global constraints

- Keep existing command signatures, poll encodings, param IDs/defaults, scene format 10, PSET behavior for files missing newer lines, and default sound. Any new engine query must be additive and documented in the same package as the engine change.
- Run production events through the owning module. Run invariants in the harness. Follow the repository's clock retirement, send budget, engine memory, fresh array and `areaCall` rules. Use bounded per-path, per-slot or per-output records and release them on teardown.
- Keep the original ordinary-read, note-routing, source-switch, posted-clock, exact-message and engine checks. When a deliberate behavior changes, identify the old assertion and test its replacement at the user's entry point.
- One issue per distinct finding in execution, with the failing case, its control and the fix commit. Several issues can share a package when their files and transition are shared. Each package adds its own `changes/<package>.md`, the affected notes and any player-visible user-page change. Land reviewed packages in batches through the repository workflow.

## Review focus

1. A child process that resumes after another save succeeded or another engine started. Inspect final bytes and every result after the late resume.
2. Lost, repeated and out-of-order save reports, including a clock set back while at capacity. Account for every accepted snapshot and refuse excess work visibly.
3. One physical key reused before the 15 Hz sweep, or two panes asking for the same logical cell. Release the original owner exactly once.
4. A PSET changing multiple settings during a held note or mid-bar. Keep unchanged runtime and distinguish device, routing, layout and note-off changes.
5. A full ii queue or two ownership changes before drain. Compare the final sequence handed to crow with the final requested mode and keep the queue limits.

## Execution order and checks

Start Tasks 1, 3, 4 and 6 independently in separate worktrees. Task 2 takes the publication primitive from Task 1. Land Task 3's engine change after Task 2 if they share `StrataFiles.sc`. Task 5 follows Task 4 in `positions.lua`. Task 7 provides the post-read conventions for Tasks 8 and 9. Task 9 consumes Task 6's TXo contract. Task 10 can run beside the PSET work and lands after Task 7 if they touch the same sequencer lines. Task 11 follows all fixes. The numbers are work packages, not severity ranks.

For each code package use systematic debugging, then TDD. First capture the reported control and failing alternate through the real entry point. Run the named unit file using `lua test/run.lua <filter>` and repeat with LuaJIT, then implement the edge, see that it turns green, update the owning Machines entry and run the full three checks before committing. The full commands are `lua test/run.lua`, `luajit test/run.lua` and `lua test/sync_check.lua`. Screen changes also require the page renders. For engine packages use a separate `STRATA_SC_PORT` and the listed areas during development, then the full `test/run_engine_check.sh` and `test/run_engine_check_313.sh` before pushing. Record time per area and collector outcomes. Each task gets spec and quality review before landing.

## Decisions for review before implementation

The proposed four-save admission window is the player-visible tradeoff. Replayable outcomes keep a missed notification from permanently consuming that window. A larger eviction queue would only move the data-loss threshold. The proposed OS publication mechanism has a feasibility gate on the supported file systems and both SC versions. A same-path write that cannot acquire a safe commit must leave a truthful pending or failure outcome. Hardware timing, physical device state and failed voice allocation need the 4.0 hardware run.
