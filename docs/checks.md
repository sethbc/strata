# Running the checks

How to run the checks, what each needs and how CI runs them. Run the Lua checks from the repo root before every commit, and the engine check when engine code or a check area changes. AGENTS.md has the short list; how the harness itself works (the stubs, the runner, the 3.13 image) is in `docs/notes/test-harness.md`.

## On norns

Copy the project to `~/dust/code/`, then restart norns from its menu (SYSTEM > RESTART), which restarts SuperCollider too and so compiles the engine's classes: every engine change needs it. maiden's `;restart` restarts only matron, norns' Lua side (norns' changelog: "`;restart` `;start` `;stop` REPL messages to control matron remotely"), so it never picks up an engine change. Watch the maiden console for errors.

## The Lua tests

- `lua test/run.lua` and `luajit test/run.lua`: the behavior tests against norns stubs (`test/norns_stubs.lua`). Tests live in test/unit/<module>_test.lua (one file per module, discovered automatically). `lua test/run.lua` runs all (as CI does); `lua test/run.lua <filter>` runs the unit files whose name contains `<filter>` (`lua test/run.lua lfos`; `pages` runs every page's file). Run your module's file while you work and the whole suite before pushing. They need only Lua 5.3 (norns' version) and LuaJIT.
  - **In parallel**: each unit file runs in a process of its own, as many at once as the machine has cores, at most 8 (`--jobs N` or `-j N` sets the number, else `STRATA_TEST_JOBS=N`; never more than the files), so a full run takes about as long as its slowest file, `ui_layout_test.lua` (about 2 minutes on a 32-core machine, at 3.8's package x5: the whole suite took 136 s under Lua 5.3 and 144 s under LuaJIT at the default 8 processes and at 4, 248 s and 225 s at 2, against 432 to 488 s and 396 to 465 s in one process). `--jobs 1` runs every test in the runner's own process and prints what the runner printed before it ran in parallel; so does a run that takes one file, and a run a test starts. A parallel run prints each file's lines whole as its process ends, every failure again just before the totals, a line `<files> unit files in <n> processes, <s> s`, and the same last line, `<tests> tests, <failures> failures`; a process that crashes or ends without its report fails the run, named. `--shard K/N` runs only shard K of N of the unit files (CI's jobs): every file is in exactly one, dealt by its weight in `UNIT_FILE_SECONDS` (`test/helpers.lua`; a file with no line takes the default weight, so a line is optional and only improves the balance: a heavy new file, over ten seconds alone, say, is worth one). A malformed option exits 2 with a usage line. Details: `docs/notes/test-harness/run-and-helpers.md` (The parallel run).
  - The engine stub rejects any `engine.*` call whose name, argument count or types do not match the engine's `addCommand` signatures, whose index or enumerated arguments are out of the engine's range, or whose `setVoiceParam`/`setGrainParam` name is not a control of the engine's SynthDefs. Every parser of the engine source skips `//` and `/* */` comments.
  - The run also includes the sync check, the AGENTS.md table check, the docs checks over the maintained docs (AGENTS.md, README.md, `ROADMAP.md`, every `.md` directly in docs/, this file among them, and every `.md` under docs/notes/, docs/user/ and docs/decisions/: commands, paths in backticks, relative links, the "Must not break" headings, the engine notes and areas matching, the user page links, freeze and lock wording, US spelling; listed in `docs/notes/test-harness/run-and-helpers.md`), the changelog fragment check, and checks that the FX SynthDefs' defaults equal the Lua param defaults and that `numVoices`, `numBuffers`, `standardBufferSeconds`, `bufferStateStride`, `bufferStateLoads`, `numModSlots`, `numFastDestinations`, `fastModNoteSlots`, `numFastLfos`, `waveformPoints`, `noteSlots` and `notePoolMax` equal the script's constants (`lib/constants.lua`, `notePoolMax` its `NOTE_POOL.max`; `BUFFER_STATE_STRIDE` and `BUFFER_STATE_LOADS` are in `lib/buffers.lua`).
  - Module safety nets: the global-reference and duplicate-global checks (Lua 5.3 with `luac` or `luac5.3` on PATH; LuaJIT skips them) and the locals probe (30 free locals in each file's main chunk and each constructor). Tests also check the includes, that a second load shares no state with the first, the constructor shape, and `MODULE_HOMES`. Details: `docs/notes/test-harness/run-and-helpers.md`.
- **Edit no source file while a check runs**: a run reads the files as it goes (each script load reads `lib/` again), so an edit mid-run can fail an unrelated test, as a layout state added or moved between a test's count of the states and its fresh loads does (#860).
- US spelling is enforced by a test (`text uses US spelling` in `test/unit/docs_test.lua`; extend its word list).
- `lua test/sync_check.lua`: every `engine.<name>(...)` call has a matching `addCommand` with the same argument count, and every command is used but those in its `PENDING_COMMANDS` (commands the engine has before the script calls them: each is listed from the engine change that adds it until the change that calls it, and calling one fails the check until its name is removed). Call engine commands only as `engine.<name>(...)`: any other use of `engine` (`engine[name](...)`, `local f = engine.voiceOn`, `local e = engine`) fails the check, which cannot see what it calls.
- Add a test to the unit file of the module you change, for every behavior change. Script state is reached through `local_value()`/`find_upvalue()` (fields of `S`, then `S.constants`, then upvalues), so a name the tests use must stay a field of `S` or `S.constants` under that name.
- The stubs mirror the real norns libraries (`~/src/norns/lua`): check behavior there before changing them. `param.t` holds numeric type codes (`params.tOPTION`, ...), so never compare it with a string (a test enforces this). The stubbed APIs and test helpers (`context.polls.fire`, `context.midi.plug`, `context.set_time`, `context.encoders.deliver`, ...) are listed in `docs/notes/test-harness/stubs.md` and `docs/notes/test-harness/clock.md`.
- `test/StrataTestNoBoot.sc.in` is deliberately not a `.sc` file: norns compiles every `.sc` under `~/dust`.

## The engine check

- `test/run_engine_check.sh [path/to/norns]` compiles the engine against a norns checkout's `sc/core` and runs `test/engine_check.scd` on a silent local scsynth with norns' 8192 KB real-time pool.
  - It needs SuperCollider and a norns checkout (`git clone https://github.com/monome/norns ~/src/norns`, or set `$NORNS_DIR`; CI uses commit `227aa0442181e3eab3fc189ee6b5342648ce7300`).
  - It uses `$SCLANG` if set, else `sclang` on `PATH`, else the macOS app.
  - It stops each sclang after `$ENGINE_CHECK_TIMEOUT` seconds (2700 by default: each shard of a full run, at most 361 s of areas, fits with room, and a full run in one sclang, whose areas sum to 1771 s (1733 s in CI's run 44395161831, and 38 s of the checks since: #809's, #828-#831's in the types area, #833-#835's and #858's in freeze and outrings, #872's and #888's in onsets, #886's and #940's in mix and lifecycle, and #885's, #889's, #890's and #946's in buffers, record and delay, less the 4 s #944's walk of the record area's state table saved), has 899 s before the check's deadline of 2670 s; the default is 1.52 times that sum, and a test in `test/unit/docs_test.lua` holds it at 1.5 times the sum the workflow's area times state, #816. CI passes `ENGINE_CHECK_TIMEOUT=570` to keep each shard below its 600 s limit; the check's own deadline is 30 s less) and at once on a compile error. Stopping sclang also stops its scsynth (descendants found with POSIX `ps`, so neither `pgrep` nor `timeout` is needed), a scsynth that outlives a crashed sclang is stopped through the PID the check writes to its work dir (#152) and waited for, up to 10 s (still running then, the run fails, exit 3), and a signal to the script (Ctrl-C, a caller's limit) stops sclang, its scsynth and the work folder and exits 130 (#331).
  - Each run boots scsynth on the UDP port in `$STRATA_SC_PORT` (57110 by default). Runs on different ports can overlap, for example one per worktree (`STRATA_SC_PORT=57141 test/run_engine_check.sh`); avoid 57120 and the few ports above it, which sclang takes for itself when several run. Two runs on the same port collide, so on a shared machine give each its own port or wrap the runs in a lock, for example `flock /tmp/strata-engine-check.lock test/run_engine_check.sh`.
  - The runner builds the engine and runs the area files `test/engine_check/<area>.scd` in a fixed order (`docs/notes/engine/structure.md`). `$STRATA_ENGINE_CHECK_AREAS` (comma- or space-separated, `STRATA_ENGINE_CHECK_AREAS=memory`) runs only the areas it names; a name with no area file fails the run. Work on an area with its own run, and run all areas before pushing: the workflow's area times (CI's run 44395161831 on `main`, 2026-11-18, with the outrings, freeze, types, onsets, mix, lifecycle, buffers, record and delay areas as the checks since left them) sum to 1771 s, about 30 minutes, and a full run in CI's shards took 1202 s on 3.14.1 at the 3.5.0 release (1098 s at 3.5's Wave 1, before the notes area's 79 s); a loaded machine can take longer. A new area adds its file, its name in `areaOrder` and its notes file. The soak (`STRATA_ENGINE_CHECK_AREAS=soak`, `docs/notes/engine/files.md`) runs only when named, never in a full run or CI.
  - A full run (no areas named) is CI's shards, read from `.github/workflows/test.yml` at each start (through `test/run_engine_check_313.sh -l`), each in a sclang of its own, one after another on the run's port (#671): every shard runs, then a line a shard (`shard <areas>: passed in <n> s`, or `failed in <n> s (exit <status>)`) and the result, which passes only when every shard passed. A signal stops the running shard, prints the lines of what ran and where it came, and exits 130; no shard starts after one whose scsynth outlived its stop. One sclang running every area in turn crashed at the start of the `modulation` area about half the time on 3.14.1 until #211's fix (#681; with it, 6 of 6 such runs passed); `STRATA_ENGINE_CHECK_ONE_SCLANG=1 test/run_engine_check.sh` still runs it. The shards' own sclang starts add about 25 s (1098 s against 1073 s in one sclang, 3.14.1, at 3.5's Wave 1). Details: `docs/notes/test-harness/engine-check-runner.md` (Full runs).
  - A run stops at once on a compile error, and fails on any `ERROR`, `WARNING`, `FAILURE`, `alloc failed`, `Too many grains` or `Strata invariant broken` line. Details: `docs/notes/test-harness/engine-check-runner.md`.
- **Soak** (on demand, not in CI or a full run): `STRATA_ENGINE_CHECK_AREAS=soak test/run_engine_check.sh` runs rounds of a 60 s load, save and every-frame check of the saved file on a high engine of its own, to stress sclang's allocation as a long session would (#131). `STRATA_SOAK_ROUNDS` (40) and `STRATA_SOAK_SECONDS` (60; 120 or 300) size it; give a long soak a longer `ENGINE_CHECK_TIMEOUT` (the check's own deadline follows, 30 s under it). Run it with SuperCollider 3.13, norns' version, to be meaningful.
- **Engine check on SuperCollider 3.13:** `test/run_engine_check_313.sh [-n runs] [-j parallel] [-o log_dir] [-1] [-l] [-c] [path/to/norns]` runs the check in Docker on CI's SuperCollider (norns' 3.13). A full run is CI's shards (read from `.github/workflows/test.yml` at each start), each in a container, and so a fresh sclang, of its own, and passes only when every shard passed (#581); `-1` runs every area in one sclang, as before, `STRATA_ENGINE_CHECK_AREAS` runs those areas in one container per run, `-l` prints the shards and `-c` classifies a log folder again. `-j` containers run at once, each on its own network; it builds its image (`test/docker/sc313/Dockerfile`) on first use and reports how many runs passed, failed or crashed (#131). Details in `docs/notes/test-harness/engine-check-runner.md`.

### On Linux

Install `supercollider-language`, `supercollider-server` and `jackd2`. scsynth needs a JACK server, and a dummy driver needs no sound card. Start one in the background, then run the check headless:

```sh
nohup jackd --no-realtime -d dummy -r 48000 -p 1024 >/tmp/jackd.log 2>&1 &
SCLANG=/usr/bin/sclang QT_QPA_PLATFORM=offscreen test/run_engine_check.sh ~/src/norns
```

If scsynth does not boot, check that JACK is running (`jack_lsp` fails when it is not) and start `jackd` again. Run JACK at 48 kHz, like norns. The check fails at once, within seconds, with `scsynth did not boot` when the server cannot start, and with `port <n> already has a server` when another run holds the port (#471, #472).

## Page renders

On demand, never in the suite or CI (they need Pillow): `lua test/render_pages.lua /tmp/strata-renders && python3 test/render_pages.py /tmp/strata-renders --font ~/src/norns/resources/norns.ttf` writes each page state's draw calls as `<page>-<state>.json` and draws them as 128×64 PNGs (scaled 4×, Pillow). The states are the script's own list plus each page record's `layout_states`. Look at them after a layout change; details in `docs/notes/lua/ui/layout-and-renders.md`. The layout tests catch overlaps on one baseline and text off-screen; the renders are the check for text over a line or box and for strings crowding on nearby baselines.

## CI

`.github/workflows/test.yml` runs the behavior tests as a job per interpreter and shard of the unit files (`lua (lua5.3, 1/2)` and `2/2`, whose Lua 5.3 job of shard 1 also runs the sync check, once a run, and `lua (luajit, 1/2)` and `2/2`), each running its shard in parallel on its runner's cores, gathered by one `lua` job that passes only when every one passed, and the engine check in seven parallel shards (`engine (<areas>)`, one runner each), gathered by one `engine` job that passes only when every shard passed. memory shares its shard only with rings, which builds no high-tier engine (#131), and runs first in it, so CI's memory figures are the area's alone; record and waveform share a shard for the times alone (#211's collector failure in waveform's 300 s check is fixed, #681: its count-error lines seen again in any shard are a regression to find, as `docs/status.md` says, not a run to repeat); since #652 the areas no longer depend on each other's order, so which areas share a shard is a choice for the times alone (files and structure, which failed together before #652, still share none: the layout kept is as balanced as any that pairs them). The shards are balanced from the per-area times the check prints, measured on SuperCollider 3.13 in one CI run (44395161831, 2026-11-18: at most about 360 s of areas a shard, buffers, loops and types, against about 1733 s for all of them), and `test/unit/docs_test.lua` checks that every area is in exactly one. The local 3.13 runner reads the same list from the workflow, so a full run there is CI's shards too (#581). Every job has a timeout: 12 minutes for each Lua job (Installs, below), 37 for each engine shard (the sum of its steps' own limits and a minute for the runner's own steps, the check under `timeout --kill-after=15 600` with `ENGINE_CHECK_TIMEOUT=570`: Installs, below) and 5 for each gathering job, which the test "every CI job has a timeout" in `test/unit/docs_test.lua` pins (#225). A new push to a pull request cancels its older runs; runs on `main` are never canceled.

**The Lua jobs and their times (3.8's package x5).** In one process each suite took 9 to 11 minutes in CI (run 44224340612: 8 min 58 s on Lua 5.3, 10 min 47 s on LuaJIT), about twice the slowest engine shard. Each Lua job now runs its shard in parallel on its runner's cores (it prints `nproc` first; GitHub documents 4 for a public repository's standard Linux runner), and the matrix's one `shard:` line sets how many shards each interpreter's suite is split into, aiming at no Lua job over 5 minutes. On a 32-core machine, one measurement each with other work running: the whole suite took 136 s (Lua 5.3) and 144 s (LuaJIT) at 4 processes, 248 s and 225 s at 2; as `--shard 1/2` and `2/2` they took 132 and 88 s at 4 processes, 130 and 117 s at 2. CI ran the one-process suite in 1.25 (Lua 5.3) to 1.6 (LuaJIT) times that machine's time, so with 4 cores one shard took about 4 minutes plus about 1 of checkout and install, and the workflow had one until 3.9's tables and walks grew the suite to 4419 tests: one shard then took 432 to 539 s on Lua 5.3 and 512 to 613 s on LuaJIT, and a LuaJIT job was canceled at the job's limit with every test passing (#991). The workflow has two since (`shard: ["1/2", "2/2"]`); a third shard gains little, since no shard runs faster than its slowest file, `ui_layout_test.lua` (about 2 minutes there; its first test alone about 95 s). Shard 1 took 264 to 331 s in five runs' jobs but one, which took 471 s on `main` (run 45320574628, LuaJIT, 4 cores), and shard 2 121 to 222 s; the job's limit is 12 minutes since #993, so that this suite still fits after a slow mirror's setup (Installs, below). The shards are not uneven by weight: both weigh the same in `UNIT_FILE_SECONDS`. Shard 1's time is `ui_layout_test.lua`'s alone (about 230 s alone on a loaded machine), so no change of `UNIT_FILE_SECONDS` shortens it; splitting that file, another change, does. `test/unit/docs_test.lua` checks that the shards are a complete `1/N` to `N/N` set, that the `lua` job needs every Lua job, and that the sync check runs once a run.

**Installs (#785).** Each engine shard installs SuperCollider, Qt and JACK, about 111 MB from the runner's Ubuntu mirror. A slow mirror (142 kB/s on the runners that used `us-east-2.ec2.archive.ubuntu.com`, against seconds on the others in the same run) canceled three of the shards at the job's limit, still downloading, run after run. So:
- **The package files are kept between runs** (`actions/cache/restore` and `actions/cache/save`, one release pinned by commit, #533). The step "List SuperCollider and JACK's packages" runs `apt-get update`, asks apt what the three packages need on a system with nothing installed (`apt-get install -s` against an empty dpkg status) and writes each file with its SHA512 from apt's lists; the cache key is `sc-debs-<ImageOS>-<arch>-<SC_APT_VERSION>-<hash of that list>`. So every shard computes the same key, whatever its image has installed (in #785's run one fleet had a library the other downloaded) and whichever mirror it uses, while a new build of any package makes a new key (apt downloads only the changed file, a new entry is saved, the old one ages out). The key hashes the whole closure, 422 package files, though an entry holds only the 119 the image lacks (about 111 MB), so a security update to any of the 422 makes a new entry of about 111 MB; old entries age out (GitHub removes one unread for 7 days, and a repository holds 10 GB). A restore with no exact hit takes the newest entry with the same prefix. The install hands apt a kept file only when its SHA512 matches: apt itself takes any file of the right size in its archive folder as downloaded (seen with apt 2.8.4 on Ubuntu 24.04 and apt 3.3), so a damaged file would only fail in dpkg. apt still decides what to install and downloads whatever the cache lacks or failed the check, first with `--download-only`; the kept folder (`$RUNNER_TEMP/sc-debs`, the runner user's, package files only) is then refilled with the list's files that this install has, and saved by the very next step when the key was not an exact hit: right after the install, whatever the engine check does later. Every shard may try to save the one key: the first does, the others log that it is taken, and neither the restore nor the save can fail a shard (`continue-on-error`, a limit of their own).
- **The Lua jobs keep theirs the same way (#993).** Each Lua job installed `lua5.3` and `luajit` straight from the mirror, under a 3-minute limit; on the runners whose mirror was slow its `apt-get update` took 73 to 131 s (13.4 MB at 114 to 221 kB/s) and the 751 kB download 32 to 63 s (12 to 24 kB/s, once after an update of 8 s), and four jobs of two pull requests were stopped at the limit with no test run (measured in 32 jobs of five runs, 45317374513, 45318591229, 45318610201, 45318613190 and 45320574628; 1 to 19 s for the update and under a second for the download on a fast mirror). Now the steps "List Lua 5.3 and LuaJIT's packages", "Restore ...", "Install Lua 5.3 and LuaJIT" and "Keep ..." do what the shard's do, by the same pinned pieces of script and the same checks: the list is the closure of the two packages from an empty dpkg status (12 files; an entry holds only the 4 the image lacks, about 751 kB), a kept file reaches apt only when its SHA512 is apt's, the download runs under `timeout 20` and then once more with `https://archive.ubuntu.com` first under `timeout 30`, and the save is the step right after the install, on a miss only. The kept folder is `$RUNNER_TEMP/lua-debs` and the key `lua-debs-<ImageOS>-<arch>-<hash of the list>`, its own: no key starts as the shard's `sc-debs-`, so neither restore takes the other's entry (a test checks it). The four Lua jobs of a run try the one key, and the first to install saves it. On a hit a slow mirror costs the Lua job its list step alone (the `apt-get update`, which the cache cannot spare: 115 s at most since #999, below), and the install takes a few seconds. On a miss on a slow mirror the job pays that list, then a download cut at 20 s (and its 5 s kill) and fetched again from `https://archive.ubuntu.com` (a second or two; 30 s at most), the unpacking and the save. By the test's figures the setup on a slow mirror, the runner's own steps included, takes about 153 s on a hit and 218 s on a miss at worst, against the 3 minutes and more the install took before, when four jobs were stopped; the first run of a pull request that has no entry of its own and no entry from `main` misses in every Lua job, and the entry its jobs save is that pull request's (its reruns read it), so `main` has an entry only once a push to `main` has run the Lua jobs.
- **Who sees an entry** (GitHub's "Restrictions for accessing a cache", in its dependency caching reference): a run reads the entries of its own branch and of the default branch, and a pull request's run also those of its base branch; an entry saved by a pull request's run belongs to its merge ref (`refs/pull/<n>/merge`), and "can only be restored by re-runs of the pull request", never by `main` or by another pull request; an entry's contents never change (a new key makes a new entry); an entry unread for 7 days is removed, and a repository holds 10 GB. So, in one pull request, the first shard whose install finishes saves the entry, and a rerun of a shard that was too slow restores it and downloads nothing; another pull request sees none of it; the entry a push to `main` saves is read by every later run of every pull request. Later pushes to the same pull request run on the same merge ref, and so should see its entries too, but GitHub's text names only re-runs.
- **apt gives up on a dead connection**: every `apt-get` takes `$APT_NETWORK_OPTIONS` (the workflow's `env`): `Acquire::Retries=1` and `Acquire::http::Timeout=15` with its `https` twin (a connection that sends nothing for 15 s is dropped; apt-transport-http(1) applies it to "the connection as well as the data"). The runner's sources name a mirror list (`mirror+file:/etc/apt/apt-mirrors.txt`: its cloud's mirror, then `https://archive.ubuntu.com/ubuntu/`), and apt tries the next mirror only once a file has failed on the first, its retries included (apt-transport-mirror(1)); one retry, the runner image's own setting, keeps that quick. On the command line these win over the image's `/etc/apt/apt.conf.d` (apt.conf(5)).
- **A slow mirror is not a dead one.** At 142 kB/s data keeps coming, no file fails, and no apt setting ends it (apt has no low-speed limit; `Dl-Limit` only caps the rate). So the install's download runs under `timeout 45` (a normal one takes 3-12 s, and none at all on a hit). If it is unfinished then, the step prints a warning, gives every mirror but `https://archive.ubuntu.com/ubuntu/` priority 9 in the runner's mirror list, and downloads again under `timeout 75`: the files already downloaded stay, the lists, their signatures and every file's hash are apt's as before (the lists are those of the `mirror+file:` source, whichever mirror serves a file), and nothing else of apt's configuration changes. Unfinished again, the step fails with an `::error::` line saying the check never ran. Tried in an Ubuntu 24.04 container whose first mirror sent `.deb` files at 150 kB/s: the first try stopped at 45 s, the second fetched 212 MB in 10 s from `archive.ubuntu.com`, and the install finished in 108 s.
- **The list's update gets the same retry (#999).** The list step's `apt-get update` reads the same mirrors, and no cache can spare it: the SHA512 list must come from lists this job's update fetched. On the runners whose mirror was `us-east-2.ec2.archive.ubuntu.com` it took 73 to 155 s (13.4 MB at 92 to 221 kB/s), against 1 to 34 s elsewhere (1 to 19 s in #993's runs, 4 to 34 s in the two runs named next), and twice it never ended: in #986's run on f003baff a shard's update fell over to `https://archive.ubuntu.com` for its first files and then sent nothing until the step's 4 minutes, and in #1004's first run a shard's sent nothing for three and a half minutes after its first files, to the step's 4, while a Lua job's was still fetching at its 3, its files failed by apt's own 15 s timeout and fetched again. So in both jobs the update runs under `timeout --kill-after=5 45`; when it is killed or fails (any exit but 0), the step prints a warning, reorders the mirror list by the install's own `sed` (every mirror but `https://archive.ubuntu.com/ubuntu/` gets priority 9) and runs the update once more under `timeout --kill-after=5 60`; when that one does not end with 0 either, the step fails with an `::error::` line before any list is read. The lists are apt's, signature-checked, whichever mirror served them (the source is `mirror+file:`), and the reorder stays for the install, which then downloads from `archive.ubuntu.com` first too. The piece is the same in both jobs and pinned verbatim as each list step's first lines (`CI_WORKFLOW.LIST_UPDATE`). A list whose update succeeds at the first try takes what it took before (7 to 38 s on a fast mirror, the apt-cache work after the update 2 to 3 s in the Lua job and 3 to 4 s in the shard); one whose first try is cut takes about 50 s and the retry (seconds from `archive.ubuntu.com`), 115 s at most when the retry succeeds (45 s, a 5 s kill, 60 s and 5 s allowed for the apt-cache work), and one where neither try ends fails by its line after 115 s at most, inside both steps' limits.
- **The hash check comes first, by test** (#786): tests in `test/unit/docs_test.lua` pin verbatim the pieces of script the cache's safety rests on, the making of the SHA512 list (the list step, from the empty dpkg status to the list's write: the sums are apt's, from its signature-checked lists), the install step's start (from its first line, which it must be, to the kept folder's assignment: nothing before the loop can shadow a command it runs, #792) and the verify-and-copy loop (the install step, from the kept folder's assignment to the loop's `done`: a kept file is copied only inside the `if` whose condition is its own check), so any edit of them fails by its first changed line and is made on purpose, with the pinned text changed in the same commit (`CI_WORKFLOW.PINNED`, a set of pieces for each job that keeps its packages: the shard and the Lua job, #993, each read with the same checks, `CI_WORKFLOW.CACHES`, and each mutation applied in its own job's text). - **A failed install is not a failing check.** A shard that failed in "List SuperCollider and JACK's packages" or "Install SuperCollider and JACK" never ran the engine check, and a Lua job that failed in "List Lua 5.3 and LuaJIT's packages" or "Install Lua 5.3 and LuaJIT" never ran its suite: rerun it (`gh run rerun <run> --failed`; the rerun reads what the shards that finished saved). Its last lines say why: the install's `::error::` line, the packages not downloaded (exit 124 or 137: unfinished on both mirrors; another exit: apt's own failure above it, such as a `Failed to fetch` line, a file that failed on every mirror); the list's `::error::apt's lists did not update`, neither of its two updates finished (exit 124 or 137) or succeeded (#999); the list's `a package has no SHA512 in apt's lists`, lists apt could not read; `The action ... has timed out`, the step's own limit (a list, or an unpacking, that hung). A restore or save that fails or times out is only a warning: the shard goes on. A check that ran to its `timeout` (exit 124, or 137 when its process had to be killed) or to its step's 11 minutes is the check's to look into. `gh run watch --exit-status` has been seen to exit 0 on a run with canceled jobs: read the `engine` job's result (`gh run view <run>`), not the watch's exit.

`main` is protected:
- every change goes through a pull request, with no approvals required;
- both jobs must pass (since the review fixes' batch landings, a branch need not be up to date with `main`: a landing branch is built on it);
- the rules apply to admins too;
- force pushes and deleting `main` are blocked;
- history must be linear: pull requests merge by rebase (or squash), never with a merge commit, and branches are updated by rebasing on `main`.
