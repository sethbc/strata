# Running the checks

How to run the checks, what each needs and how CI runs them. Run the Lua checks from the repo root before every commit, and the engine check when engine code or a check area changes. AGENTS.md has the short list; how the harness itself works (the stubs, the runner, the 3.13 image) is in `docs/notes/test-harness.md`.

## On norns

Copy the project to `~/dust/code/`, then restart norns from its menu (SYSTEM > RESTART), which restarts SuperCollider too and so compiles the engine's classes: every engine change needs it. maiden's `;restart` restarts only matron, norns' Lua side (norns' changelog: "`;restart` `;start` `;stop` REPL messages to control matron remotely"), so it never picks up an engine change. Watch the maiden console for errors.

## The Lua tests

- `lua test/run.lua` and `luajit test/run.lua`: the behavior tests against norns stubs (`test/norns_stubs.lua`). Tests live in test/unit/<module>_test.lua (one file per module, discovered automatically). `lua test/run.lua` runs all (as CI does); `lua test/run.lua <filter>` runs the unit files whose name contains `<filter>` (`lua test/run.lua lfos`; `pages` runs every page's file). Run your module's file while you work and the whole suite before pushing. They need only Lua 5.3 (norns' version) and LuaJIT.
  - The engine stub rejects any `engine.*` call whose name, argument count or types do not match the engine's `addCommand` signatures, whose index or enumerated arguments are out of the engine's range, or whose `setVoiceParam`/`setGrainParam` name is not a control of the engine's SynthDefs. Every parser of the engine source skips `//` and `/* */` comments.
  - The run also includes the sync check, the AGENTS.md table check, the docs checks over the maintained docs (AGENTS.md, README.md, `ROADMAP.md`, every `.md` directly in docs/, this file among them, and every `.md` under docs/notes/, docs/user/ and docs/decisions/: commands, paths in backticks, relative links, the "Must not break" headings, the engine notes and areas matching, the user page links, freeze and lock wording, US spelling; listed in `docs/notes/test-harness/run-and-helpers.md`), the changelog fragment check, and checks that the FX SynthDefs' defaults equal the Lua param defaults and that `numVoices`, `numBuffers`, `standardBufferSeconds`, `bufferStateStride`, `bufferStateLoads`, `numModSlots`, `numFastDestinations`, `fastModNoteSlots`, `numFastLfos`, `waveformPoints`, `noteSlots` and `notePoolMax` equal the script's constants (`lib/constants.lua`, `notePoolMax` its `NOTE_POOL.max`; `BUFFER_STATE_STRIDE` and `BUFFER_STATE_LOADS` are in `lib/buffers.lua`).
  - Module safety nets: the global-reference and duplicate-global checks (Lua 5.3 with `luac` or `luac5.3` on PATH; LuaJIT skips them) and the locals probe (30 free locals in each file's main chunk and each constructor). Tests also check the includes, that a second load shares no state with the first, the constructor shape, and `MODULE_HOMES`. Details: `docs/notes/test-harness/run-and-helpers.md`.
- US spelling is enforced by a test (`text uses US spelling` in `test/unit/docs_test.lua`; extend its word list).
- `lua test/sync_check.lua`: every `engine.<name>(...)` call has a matching `addCommand` with the same argument count, and every command is used but those in its `PENDING_COMMANDS` (commands the engine has before the script calls them: each is listed from the engine change that adds it until the change that calls it, and calling one fails the check until its name is removed). Call engine commands only as `engine.<name>(...)`: any other use of `engine` (`engine[name](...)`, `local f = engine.voiceOn`, `local e = engine`) fails the check, which cannot see what it calls.
- Add a test to the unit file of the module you change, for every behavior change. Script state is reached through `local_value()`/`find_upvalue()` (fields of `S`, then `S.constants`, then upvalues), so a name the tests use must stay a field of `S` or `S.constants` under that name.
- The stubs mirror the real norns libraries (`~/src/norns/lua`): check behavior there before changing them. `param.t` holds numeric type codes (`params.tOPTION`, ...), so never compare it with a string (a test enforces this). The stubbed APIs and test helpers (`context.polls.fire`, `context.midi.plug`, `context.set_time`, `context.encoders.deliver`, ...) are listed in `docs/notes/test-harness/stubs.md` and `docs/notes/test-harness/clock.md`.
- `test/StrataTestNoBoot.sc.in` is deliberately not a `.sc` file: norns compiles every `.sc` under `~/dust`.

## The engine check

- `test/run_engine_check.sh [path/to/norns]` compiles the engine against a norns checkout's `sc/core` and runs `test/engine_check.scd` on a silent local scsynth with norns' 8192 KB real-time pool.
  - It needs SuperCollider and a norns checkout (`git clone https://github.com/monome/norns ~/src/norns`, or set `$NORNS_DIR`; CI uses commit `227aa0442181e3eab3fc189ee6b5342648ce7300`).
  - It uses `$SCLANG` if set, else `sclang` on `PATH`, else the macOS app.
  - It stops each sclang after `$ENGINE_CHECK_TIMEOUT` seconds (1800 by default, which a full run in one sclang, 1073 s on 3.14.1 at 3.5's Wave 1, fits with about 12 minutes to spare; CI passes `ENGINE_CHECK_TIMEOUT=570` to keep each shard below its 600 s limit; the check's own deadline is 30 s less) and at once on a compile error. Stopping sclang also stops its scsynth (descendants found with POSIX `ps`, so neither `pgrep` nor `timeout` is needed), a scsynth that outlives a crashed sclang is stopped through the PID the check writes to its work dir (#152) and waited for, up to 10 s (still running then, the run fails, exit 3), and a signal to the script (Ctrl-C, a caller's limit) stops sclang, its scsynth and the work folder and exits 130 (#331).
  - Each run boots scsynth on the UDP port in `$STRATA_SC_PORT` (57110 by default). Runs on different ports can overlap, for example one per worktree (`STRATA_SC_PORT=57141 test/run_engine_check.sh`); avoid 57120 and the few ports above it, which sclang takes for itself when several run. Two runs on the same port collide, so on a shared machine give each its own port or wrap the runs in a lock, for example `flock /tmp/strata-engine-check.lock test/run_engine_check.sh`.
  - The runner builds the engine and runs the area files `test/engine_check/<area>.scd` in a fixed order (`docs/notes/engine/structure.md`). `$STRATA_ENGINE_CHECK_AREAS` (comma- or space-separated, `STRATA_ENGINE_CHECK_AREAS=memory`) runs only the areas it names; a name with no area file fails the run. Work on an area with its own run, and run all areas before pushing: the workflow's area times sum to 1179 s, about 20 minutes, and a full run in CI's shards took 1202 s on 3.14.1 at the 3.5.0 release (1098 s at 3.5's Wave 1, before the notes area's 79 s); a loaded machine can take longer. A new area adds its file, its name in `areaOrder` and its notes file. The soak (`STRATA_ENGINE_CHECK_AREAS=soak`, `docs/notes/engine/files.md`) runs only when named, never in a full run or CI.
  - A full run (no areas named) is CI's shards, read from `.github/workflows/test.yml` at each start (through `test/run_engine_check_313.sh -l`), each in a sclang of its own, one after another on the run's port (#671): every shard runs, then a line a shard (`shard <areas>: passed in <n> s`, or `failed in <n> s (exit <status>)`) and the result, which passes only when every shard passed. A signal stops the running shard, prints the lines of what ran and where it came, and exits 130; no shard starts after one whose scsynth outlived its stop. One sclang running every area in turn crashed at the start of the `modulation` area about half the time on 3.14.1 until #211's fix (#681; with it, 6 of 6 such runs passed); `STRATA_ENGINE_CHECK_ONE_SCLANG=1 test/run_engine_check.sh` still runs it. The shards' own sclang starts add about 25 s (1098 s against 1073 s in one sclang, 3.14.1, at 3.5's Wave 1). Details: `docs/notes/test-harness/engine-check-runner.md` (Full runs).
  - A run stops at once on a compile error, and fails on any `ERROR`, `WARNING`, `FAILURE`, `alloc failed`, `Too many grains` or `Strata invariant broken` line. Details: `docs/notes/test-harness/engine-check-runner.md`.
- **Soak** (on demand, not in CI or a full run): `STRATA_ENGINE_CHECK_AREAS=soak test/run_engine_check.sh` runs rounds of a 60 s load, save and every-frame check of the saved file on a high engine of its own, to stress sclang's allocation as a long session would (#131). `STRATA_SOAK_ROUNDS` (40) and `STRATA_SOAK_SECONDS` (60; 120 or 300) size it; give a long soak a longer `ENGINE_CHECK_TIMEOUT` (the check's own deadline follows, 30 s under it). Run it with SuperCollider 3.13, norns' version, to be meaningful.
- **Engine check on SuperCollider 3.13:** `test/run_engine_check_313.sh [-n runs] [-j parallel] [-o log_dir] [-1] [-l] [-c] [path/to/norns]` runs the check in Docker on CI's SuperCollider (norns' 3.13). A full run is CI's shards (read from `.github/workflows/test.yml` at each start), each in a container, and so a fresh sclang, of its own, and passes only when every shard passed (#581); `-1` runs every area in one sclang, as before, `STRATA_ENGINE_CHECK_AREAS` runs those areas in one container per run, `-l` prints the shards and `-c` classifies a log folder again. `-j` containers run at once, each on its own network; it builds its image (`test/docker/sc313/Dockerfile`) on first use and reports how many runs passed, failed or crashed (#131). Details in `docs/notes/test-harness/engine-check-runner.md`.

### On Linux

Install `supercollider-language`, `supercollider-server` and `jackd2`. scsynth needs a JACK server, and a dummy driver needs no sound card. Start one in the background, then run the check headless:

```sh
nohup jackd --no-realtime -d dummy -r 48000 -p 1024 >/tmp/jackd.log 2>&1 &
SCLANG=/usr/bin/sclang QT_QPA_PLATFORM=offscreen test/run_engine_check.sh ~/src/norns
```

If scsynth does not boot, check that JACK is running (`jack_lsp` fails when it is not) and start `jackd` again. Run JACK at 48 kHz, like norns. The check fails at once, within seconds, with `scsynth did not boot` when the server cannot start, and with `port <n> already has a server` when another run holds the port (#471, #472).

## Page renders

On demand, never in the suite or CI (they need Pillow): `lua test/render_pages.lua /tmp/strata-renders && python3 test/render_pages.py /tmp/strata-renders --font ~/src/norns/resources/norns.ttf` writes each page state's draw calls as `<page>-<state>.json` and draws them as 128×64 PNGs (scaled 4×, Pillow). The states are the script's own list plus each page record's `layout_states`. Look at them after a layout change; details in `docs/notes/lua/ui/layout-and-renders.md`. The layout tests catch overlaps on one baseline and text off-screen; the renders are the check for text over a line or box and for strings crowding on nearby baselines.

## CI

`.github/workflows/test.yml` runs the behavior tests as two parallel jobs (`lua (lua5.3)`, which also runs the sync check, and `lua (luajit)`), gathered by one `lua` job that passes only when both passed, and the engine check in seven parallel shards (`engine (<areas>)`, one runner each), gathered by one `engine` job that passes only when every shard passed. memory shares its shard only with rings, which builds no high-tier engine (#131), and runs first in it, so CI's memory figures are the area's alone; record and waveform share a shard for the times alone (#211's collector failure in waveform's 300 s check is fixed, #681: its count-error lines seen again in any shard are a regression to find, as `docs/status.md` says, not a run to repeat); since #652 the areas no longer depend on each other's order, so which areas share a shard is a choice for the times alone (files and structure, which failed together before #652, still share none: the layout kept is as balanced as any that pairs them). The shards are balanced from the per-area times the check prints, measured on SuperCollider 3.13 at 3.5.0 (at most about 236 s of areas a shard, lifecycle, files, positions and notes, against about 1179 s for all of them), and `test/unit/docs_test.lua` checks that every area is in exactly one. The local 3.13 runner reads the same list from the workflow, so a full run there is CI's shards too (#581). Every job has a timeout: 15 minutes for each Lua suite and each engine shard (the shard's check runs under `timeout 600` with `ENGINE_CHECK_TIMEOUT=570`) and 5 for each gathering job, which the test "every CI job has a timeout" in `test/unit/docs_test.lua` pins (#225). A new push to a pull request cancels its older runs; runs on `main` are never canceled.

**Installs (#785).** Each engine shard installs SuperCollider, Qt and JACK, about 111 MB from the runner's Ubuntu mirror. A slow mirror (142 kB/s on the runners that used `us-east-2.ec2.archive.ubuntu.com`, against seconds on the others in the same run) canceled three of the shards at the job's limit, still downloading, run after run. So:
- **The package files are kept between runs** (`actions/cache/restore` and `actions/cache/save`, one release pinned by commit, #533). The step "List SuperCollider and JACK's packages" runs `apt-get update`, asks apt what the three packages need on a system with nothing installed (`apt-get install -s` against an empty dpkg status) and writes each file with its SHA512 from apt's lists; the cache key is `sc-debs-<ImageOS>-<arch>-<SC_APT_VERSION>-<hash of that list>`. So every shard computes the same key, whatever its image has installed (in #785's run one fleet had a library the other downloaded) and whichever mirror it uses, while a new build of any package makes a new key (apt downloads only the changed file, a new entry is saved, the old one ages out). A restore with no exact hit takes the newest entry with the same prefix. The install hands apt a kept file only when its SHA512 matches: apt itself takes any file of the right size in its archive folder as downloaded (seen with apt 2.8.4 on Ubuntu 24.04 and apt 3.3), so a damaged file would only fail in dpkg. apt still decides what to install and downloads whatever the cache lacks or failed the check, first with `--download-only`; the kept folder (`$RUNNER_TEMP/sc-debs`, the runner user's, package files only) is then refilled with the list's files that this install has, and saved by the very next step when the key was not an exact hit: right after the install, whatever the engine check does later. Every shard may try to save the one key: the first does, the others log that it is taken, and neither the restore nor the save can fail a shard (`continue-on-error`, a limit of their own). The Lua suites' install (two small packages) is not cached.
- **Who sees an entry** (GitHub's "Restrictions for accessing a cache", in its dependency caching reference): a run reads the entries of its own branch and of the default branch, and a pull request's run also those of its base branch; an entry saved by a pull request's run belongs to its merge ref (`refs/pull/<n>/merge`), and "can only be restored by re-runs of the pull request", never by `main` or by another pull request; an entry's contents never change (a new key makes a new entry); an entry unread for 7 days is removed, and a repository holds 10 GB. So, in one pull request, the first shard whose install finishes saves the entry, and a rerun of a shard that was too slow restores it and downloads nothing; another pull request sees none of it; the entry a push to `main` saves is read by every later run of every pull request. Later pushes to the same pull request run on the same merge ref, and so should see its entries too, but GitHub's text names only re-runs.
- **apt gives up on a dead connection**: every `apt-get` takes `$APT_NETWORK_OPTIONS` (the workflow's `env`): `Acquire::Retries=1` and `Acquire::http::Timeout=15` with its `https` twin (a connection that sends nothing for 15 s is dropped; apt-transport-http(1) applies it to "the connection as well as the data"). The runner's sources name a mirror list (`mirror+file:/etc/apt/apt-mirrors.txt`: its cloud's mirror, then `https://archive.ubuntu.com/ubuntu/`), and apt tries the next mirror only once a file has failed on the first, its retries included (apt-transport-mirror(1)); one retry, the runner image's own setting, keeps that quick. On the command line these win over the image's `/etc/apt/apt.conf.d` (apt.conf(5)).
- **A slow mirror is not a dead one.** At 142 kB/s data keeps coming, no file fails, and no apt setting ends it (apt has no low-speed limit; `Dl-Limit` only caps the rate). So the install's download runs under `timeout 45` (a normal one takes 3-12 s, and none at all on a hit). If it is unfinished then, the step prints a warning, gives every mirror but `https://archive.ubuntu.com/ubuntu/` priority 9 in the runner's mirror list, and downloads again under `timeout 75`: the files already downloaded stay, the lists, their signatures and every file's hash are apt's as before (the lists are those of the `mirror+file:` source, whichever mirror serves a file), and nothing else of apt's configuration changes. Unfinished again, the step fails with an `::error::` line saying the check never ran. Tried in an Ubuntu 24.04 container whose first mirror sent `.deb` files at 150 kB/s: the first try stopped at 45 s, the second fetched 212 MB in 10 s from `archive.ubuntu.com`, and the install finished in 108 s.
- **Each install step has its own limit** (`timeout-minutes`): 2 minutes to list the packages, 3 to install them (both tries and the unpacking, about 25 s, fit), 3 for the Lua suites' install. A slow download fails the step by its own name, about 2.5 minutes into the job, and the check keeps its 600 s; tests in `test/unit/docs_test.lua` pin the options, the limits, the cache's steps and the second mirror.
- **A failed install is not a failing check.** A shard that failed in "List SuperCollider and JACK's packages" or "Install SuperCollider and JACK" (its `::error::` line, `The action ... has timed out`, or a `Failed to fetch` line) never ran the engine check: rerun it (`gh run rerun <run> --failed`; the rerun reads what the shards that finished saved). A shard canceled at the job's 15 minutes with "Engine check" running is the check's to look into. `gh run watch --exit-status` has been seen to exit 0 on a run with canceled jobs: read the `engine` job's result (`gh run view <run>`), not the watch's exit.

`main` is protected:
- every change goes through a pull request, with no approvals required;
- both jobs must pass (since the review fixes' batch landings, a branch need not be up to date with `main`: a landing branch is built on it);
- the rules apply to admins too;
- force pushes and deleting `main` are blocked;
- history must be linear: pull requests merge by rebase (or squash), never with a merge commit, and branches are updated by rebasing on `main`.

**Pins:** norns commit `227aa0442181e3eab3fc189ee6b5342648ce7300` (the engine is compiled against its `sc/core`), SuperCollider `1:3.13.0+repack-1ubuntu3` (Ubuntu 24.04's package; norns ships 3.13.0) and `actions/checkout` and `actions/cache` by commit (a test pins every action to a full commit with its version in a comment, #533). The workflow's comments say how to move each pin.
