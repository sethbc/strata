## Must not break

- **Every `readData` reads into a fresh array** (`freshReadArray`), never one an earlier read filled: reusing a `FloatArray` across reads makes sclang 3.13 (norns' version) abort a while later in its garbage collector (#131). This covers `fileDecodes` (each decode chunk) and `interleaveFiles` (each left and right chunk). A structure test checks every `readData` in the engine.
- **No sclang function per sample** in the engine's sample paths (the interleave, the decode check): sclang's collector fails under millions of small allocations (below, sclang's garbage collector under heavy allocation). `interleaveChunk` clips and interleaves with C primitives only; a structure test checks it, `interleaveKeys`, `fileDecodes` and the interleave's chunk loop. Saved files stay byte for byte what the old per-frame loop wrote.
- **File writes** go to a `<path>.<instanceTag>-<generation>.part` file and are renamed into place. Never open the final path for writing. The newest write to a path wins, and two writes never mix.
- `deleteStaleParts` deletes only `.part` files and `writeSlot`'s temporary float files older than `stalePartAge`, and only in absolute directories below the root (`stalePartDirs`: `scratchDir`, its parent and the settings folder the performance area used).
- A write clips samples beyond ±1 symmetrically to ±`int16Peak`, never wraps.
- A write whose temporary files hold fewer frames than the slot's valid length, or whose output reads back short (a full disk), fails: nothing is renamed, the file already at the path stays, the `.part` is deleted and `strata: cannot write <path> (...)` is posted.
- Every `saveBuffer` whose write ends is reported exactly once on `bufferSaveResult`, written only once the file is in place (after the rename), failed otherwise; a write abandoned for a newer one reports nothing. Lua says a save is saved only from that report (#127).
- A write's routine runs inside `try`: an sclang error in it is posted as `strata: cannot write <path> (<error class>)` (never with the word the engine check fails on), closes every sound file the interleave opened (each close in its own `try`), deletes its temporary and `.part` files and, if it is still the newest write, removes its `writeGenerations` entry and reports failed. A folder at the path fails the write before the rename (`mv -f` would move the file into it).
- The engine check never writes into `~/dust`: it points `scratchDir` at a temporary directory.
- A chunk loop in a routine (the interleave, a long file's decode check) waits through `yieldToCommands`, never a plain `wait`: a routine whose chunks outlast its waits falls behind its logical time, and SystemClock then runs it again at once without releasing sclang's lock, so every OSC message (matron's commands) waits until the loop ends.

## File writes

`writeSlot(index, path, done)` (scratch takes and `saveBuffer`) has the server write each mono buffer's valid frames to a temporary float file, then sclang interleaves them in 8192-frame chunks (`interleaveChunk`, C primitives only: below; yielding `writeChunkWait`, 1 ms, between chunks through `yieldToCommands`) into a stereo 16-bit WAV at the content's rate and deletes the temporaries; it creates no synth nodes. The buffers are float and `record_level` goes to 2, so a take can hold samples beyond ±1: the interleave clips every sample to ±`int16Peak` (32767 / 32768), so the file is clipped deliberately and symmetrically (+32767 / -32767) whatever libsndfile's own float-to-int conversion does (without its clipping mode it wraps; with it, it clips to +32767 / -32768). Writes to the same path can overlap (a full 16 s take is still being written when the next, shorter take completes), so each write gets a generation number in `writeGenerations[path]`, interleaves into its own `path.<instanceTag>-<generation>.part` file (`instanceTag` is `UniqueID.next` at `alloc`, so two engine instances in one sclang session, before and after a script reload, never share a `.part` or temporary float file `strata-buf<n>-<tag>-<gen>-<L|R>.wav`), and renames it into place (`mv -f`, atomic on one filesystem; sclang has no `File.rename`) only if it is still the newest write for that path. An older write checks after every chunk, abandons as soon as a newer one starts, and deletes its `.part`. The newest write always wins, two writes never mix, and a reader never sees a half-written file. The newest write removes its `writeGenerations` entry when it ends, whether it succeeded or failed (a directory that cannot be made, `File.mkdir` throwing, is caught and reported as `cannot write`); an abandoned write leaves the newer one's entry. `alloc` calls `deleteStaleParts`, which deletes the `*.part` files a crash left in `scratchDir` (scratch takes) and in its parent (`saveBuffer`'s `<date>-buf<n>.wav.<tag>-<gen>.part` in `_path.audio/strata/`, visible in the file browser), and `writeSlot`'s temporary float files (`strata-buf*-*.wav`) in `Platform.defaultTempDir`; nothing else, and only files last modified more than `stalePartAge` (60 s) ago (`File.mtime` against `Date.getDate.rawSeconds`). `File.mtime` throws for a file deleted since the glob, so it is wrapped in `try`: such a file is skipped silently, while one that is still there (or whose existence cannot be read either: a directory without search permission makes `File.exists` throw too) is left and posted (`strata: cannot read when <path> was last written`); `deleteStaleParts` returns those paths. A temporary float file is written just before its interleave opens it, and deleting an open file does not stop it being read, so the age check also keeps a running write's files: after a script reload in the same sclang session the previous instance's write routine may still be interleaving, and a running write touches its `.part` with every chunk. `stalePartDirs` picks the directories: `scratchDir` (with `~` expanded, trailing slash dropped), its `dirname` and the settings folder the performance area used at alloc (`allocSettingsDirectory`: `settingsDir`, or `~/dust/data/strata/`, where a crash can leave `performance_active.data.<tag>-<gen>.part` or Lua's `performance.data.part`), each listed once, keeping only absolute paths below the root, so an empty, relative (`"."`, `"scratch/"`, whose `dirname` is `"."`) or root `scratchDir` never globs the working directory or `/` (never `standardizePath` it: that turns `"."` into the working directory). `test/run_engine_check.sh` starts sclang in its temp dir, so the check's working-directory marker never lands in the caller's directory. Never open the final path directly for writing: `SoundFile.openWrite` truncates it, and libsndfile rewrites the header on `close`. The engine check sets `writeChunkWait` to 0.02 s so the overlap is certain.

**Scratch directory**: `scratchDir` (engine variable, settable) defaults to `Platform.userHomeDir +/+ "dust/audio/strata/scratch/"`, which equals Lua's `_path.audio .. "strata/scratch/"` on norns; it is created on demand before writing. `test/engine_check.scd` points it at a temporary directory so the check never writes into `~/dust`.

**Yielding to commands.** `yieldToCommands(wait)` waits `wait.max((Main.elapsedTime - thisThread.seconds) + commandGap)`: `wait` from the routine's logical time when it is on time (as a plain wait would), and otherwise until `commandGap` (0.2 ms) of real time from now. Measured with sclang 3.14: a `SystemClock` routine doing 20 ms of work per chunk with a plain `0.001.wait` let no OSC message in for its whole 2 s (the scheduler's batch reruns a task due in the past without releasing the language lock), while the same loop waking in the real future let every message in within one chunk. The interleave's old plain `writeChunkWait.wait` had that fault whenever a chunk took more than 1 ms (any long save on a Pi). The engine check sets `writeChunkWait` to 0.1 ms during a 60 s save and requires a message sent meanwhile to be handled before the save ends.

**Short writes.** `interleaveFiles(sourcePaths, path, sampleRate, keepGoing, frames)` compares each temporary file's `numFrames` with the slot's `frames` before opening the output (the server's `/b_write` stops short when the disk fills; a 300 s save needs about 115 MB of temporaries) and reads the finished `.part` back for its frame count. Either shortfall returns false, so `writeSlot` deletes the `.part` and keeps the old file, and posts `strata: cannot write <path> (a temporary file holds n of m frames: is the disk full?)` or `(n of m frames written: ...)`, as any failed write posts `cannot write`. A failed save is reported to Lua (below). The engine check simulates a short temporary file by giving a slot more valid frames than its buffers hold (`/b_write` clips to the buffer's end).

**Long saves** (high tier). The interleave is the same `interleaveChunk`. The temporary float files are one mono file per channel: for 300 s, 300 x 48000 x 4 bytes = 57.6 MB each, 115 MB per save, in `Platform.defaultTempDir`. Measured on a desktop (sclang 3.14): a 60 s save takes about 0.4 s, a 300 s save about 1.9 s (1758 chunks; with `writeChunkWait` 1 ms most of that is waiting, since each chunk takes under 1 ms there), a 300 s load about 0.4-0.65 s. The 300 s save time on a Pi 4 is on the 3.2 hardware list: above 10 s, the follow-up is to write the temporaries as `int16` (half the data) or to use `sox -M` when it is on the path, keeping this loop as the fallback, under the same `.part` and generation rules.

**Save results** (`bufferSaveResult`, #127). The files area owns `saveBuffer` (`addFileCommands`) and its poll. `saveSlot(index, path)` ignores a slot out of range, counts the slot's saves in `bufferSaves` (`areaState[\files][\saves]`, from 1 at alloc; Lua's `save_buffer` counts the same commands in `buffers[slot].saves_sent`) and calls `writeSlot` with a `done` function. `writeSlot` calls `done.value(written)` exactly once when a write ends (through `finish`, guarded by a `reported` flag): false at once for an empty slot (`frames < 1`); in the write's routine, only while it is still the newest write for its path (`current`), true once the `mv -f` succeeded and false when the interleave failed (a folder that cannot be made, a short temporary file or output), a folder is at the path (`PathName(path).isFolder`: `mv -f` would move the file into it and succeed) or the rename failed. The routine's body is wrapped in `try`: an sclang error anywhere in it (a read, a delete, the interleave) is posted as `strata: cannot write <path> (<error class>)`, closes every sound file the interleave had opened (`interleaveFiles` adds the sources, the output and the read-back file to the routine's `openFiles` list; each close that is still needed runs in its own `try`, so a close that fails never skips the report), deletes the temporary float files and the `.part`, and, only if the write is still the newest for its path, removes its `writeGenerations` entry and reports failed, so a save never waits forever for its report. The engine check injects such an error through `interleaveFaultHook` (`areaState[\files][\interleaveFaultHook]`, nil on norns), which `interleaveFiles` calls with the path, a stage and `openFiles`: `\start` before it opens any file, `\open` once the temporary files and the output are open. The check throws at each stage and asserts one failed report, no entry or file left, and every opened sound file closed. An abandoned write never calls it: the newer write to the same path reports its own end, and Lua's paths differ per slot and per second, so only a save repeated within one second is ever abandoned. Scratch takes pass no `done`. The report is one float, `bufferSaveResultValue(i, save, failed)` = `(save * 2 + failed) * numBuffers + i`, the layout of `bufferLoadFailed` (one float per message, since matron's `/poll/value` is typed `"if"`), exact for the first 2^20 saves of a slot. The poll is not periodic (`addPoll(\bufferSaveResult, func, false)`, sent only through `bufferSaveResultPoll.update`; its function returns the last value, 0.0 before any report, which names save 0, never sent). Why a result rather than only failures: a failure-only report cannot tell Lua when a save has succeeded, so its flash would have to claim success before the write ends (a long save on a Pi takes seconds) and correct itself later, or never confirm. With the result, Lua shows `saving buf <n>` at once and `saved buf <n>` or `buf <n> save failed` from the report (see `docs/notes/lua/buffers.md`). A save of a slot that a later load, clear or recording changed still reports its own file: the server's `/b_write` was queued before the change. The engine check asserts each case: written, the newer of two writes to one path (either order), a folder that cannot be made, an empty slot, a short write, an error thrown inside the write (one failed report, no entry or file left), a save onto a non-empty folder (one failed report, the folder unchanged), an out-of-range slot (nothing counted or reported) and a 60 s save on a high engine of its own.

## sclang's garbage collector under heavy allocation (#131, a platform limit)

norns ships SuperCollider 3.13.0. Its sclang collector keeps its scan credit in an `int32 mNumToScan` (`lang/LangSource/GC.h`), raised by every allocation (`1 << sizeclass`: a 64 KB Signal adds 4096, a frame a few); a frame of a function that needs no heap context is allocated without a collection, so millions of small calls in a row run the count up until it overflows and corrupts the collector: a failed count assertion, a segfault or a hang, some time later, wherever the collector next runs. 3.14 made the count `int64` (upstream PR 6261, whose reproducer segfaults 3.13 in 3 of 3 runs and passes 3.14.1), but 3.14.1 is not immune: a full engine check on it has also ended in the same count assertion (once, in the performance area; a rerun passed), so at least one more collector bug is involved (3.14.1 still has upstream issue 7711's frame use-after-free). Strata never asks other projects for changes: this is a fixed platform constraint on every version it runs on, and Strata keeps its allocation low instead, which lowers the risk on both.

- **Engine code** runs no sclang function per sample. `interleaveChunk` clips each chunk with the Signal `clip` primitive, turns it into an Array of Floats with `at` and an index Array (`interleaveKeys`, built once per write by the `(a, b .. c)` series primitive) and places it with `putEach` (keys and values both Arrays: the primitive reads both as slots, so a FloatArray or Signal there is misread). `freshReadArray` makes a Signal, so a chunk read from a file can be clipped directly. The saved bytes are those of the old per-frame loop (`left.size.do({ arg frame; ... })`, one sclang frame per sample): a 60 s stereo comparison of random samples up to ±1.6, with ±1, ±`int16Peak` and 0 in them, wrote identical files. Measured with sclang 3.14 on a desktop: that 60 s interleave fell from 2.88 M allocations (`gcInfo`'s `nalloc`) and 0.31 s to 2.5 k and 0.06 s; the engine check's 60 s save from about 0.5 s to 0.23 s, the 16 s write stays at 0.15 s (the server's `/b_write` dominates).
- **The engine check** builds its test sound with primitives too (`h.repeating`, `h.stereoOf`, `h.periodic`, `h.rampSignal`, `h.noise`; `docs/notes/engine/structure.md`) and compares a long saved file with the file it was loaded from in every sample, a chunk at a time into fresh Signals (`h.sameFrames`, where it used to read 23 MB into one array and look at spots). A first version that built the expected chunk from index Arrays (65536 slots each, which the collector must scan) crashed a 300 s soak on 3.13 by the eighth round; comparing raw Signals passes. Before, its file builders made about 15 M function calls (`FloatArray.fill(n, { ... })`), and the files and buffers areas allocated about 35 M and 30 M objects, against under 5 M for any other area; now 1.2 M and 1.5 M, and the whole check about 17 M instead of 81 M (sclang 3.14, `gcInfo`'s `nalloc` around each area).
- **Measured on 3.13** (16 full checks in parallel, Ubuntu 24.04's 3.13.0 in a container): before, 10 of 16 completed, and 6 crashed (core dumps, hangs until the timeout, failed count assertions), five at the end of the files area or early in effects, one in buffers' long-file checks; after, 32 of 32 completed with no crash (two failed one load-sensitive reverb measurement, the FDN's RT60 against FreeVerb2's, which a baseline run came within 1% of failing). On 3.14.1 (8 full checks in parallel): 6 of 8 before (two failed count assertions just after the files area), 8 of 8 after.
- **CI** runs the check in four shards, each in its own sclang, so no sclang's allocation adds up over the whole check; freeze and memory, the heaviest high-tier areas, are in different shards.
- **The soak** (`STRATA_ENGINE_CHECK_AREAS=soak test/run_engine_check.sh`, `test/engine_check/soak.scd`, never in CI or a full run) repeats a long session's long-file work on a high engine: each round loads a 60 s file into the next slot (the decode check and the server's read), saves it (the interleave), checks the saved file in every frame and clears the slot. `STRATA_SOAK_ROUNDS` (40) and `STRATA_SOAK_SECONDS` (60, 120 or 300) size it, and `STRATA_SOAK_CHECK=length` checks only the saved file's length (the engine's allocation without the check's reads); a longer soak needs a longer `ENGINE_CHECK_TIMEOUT`. Run it on 3.13 to be meaningful: 40 rounds of 60 s pass on 3.14 in about 25 s, of 300 s on 3.13 in about 95 s.
- **What the 300 s soak shows on 3.13** (`STRATA_SOAK_SECONDS=300`, 40 rounds, three to six containers at once): with the old per-frame interleave and `STRATA_SOAK_CHECK=length` (the engine's work only), 3 of 3 crashed, each in the ninth round; with `interleaveChunk`, 2 of 6 passed with `length` (two crashed before the second round, two in the ninth or tenth) and 3 of 3 with the every-frame check; with an inlined `while` interleave (no frames, but 5x slower), 2 of 3. So the interleave was one heavy load, and long high-tier sessions on 3.13 are still at risk: the crash near the ninth round in every variant points at something else in a long session's path (the 300 s load, the server's temporary files, or the soak's own 300 s source). Users can notice this only on the high tier with long buffers: short buffers and occasional saves allocate far less. Still open on #131.

Decoding a file before it loads (`fileDecodes`, `loadShortfallFrames`, the long-file check) is under Damaged files and failed reads and Long files in `docs/notes/engine/buffers.md`.
