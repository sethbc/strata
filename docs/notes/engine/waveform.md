## Must not break

- `waveformPoints` (64) equals Lua's `WAVEFORM_POINTS` (`lib/constants.lua`); a test reads both.
- `peaksPath(index)` is under `allocSettingsDirectory`, the folder this engine used at alloc, never `settingsDirectory`: `buildEngine` restores `settingsDir` after a build, so `settingsDirectory` would write peaks into `~/dust` from the check.
- The peak buffers (eight 64-frame mono buffers, `areaState[\waveform][\peakBuffers]`, `slotPeakBuffer(index)`) are allocated in `allocState` and freed in the area's `free`, so nothing reads a freed buffer.
- **The peak scan allocates nothing per sample** (#131): only `fileDecodes`' chunk arrays (fresh, bin-aligned) and one 64-value `FloatArray` per load; a bin's peak is `Signal`'s `peak`, a C primitive. `maxItem` and `minItem` are not primitives: `Collection` runs a sclang function for every sample (880 chunks of 16384 stereo frames, a 300 s load: 3.6-3.9 s of sclang against 13-23 ms for `peak`, on 3.13 and 3.14.1). No `abs`, `copyRange`, `collect` or per-bin array either. A source scan in `test/unit/structure_test.lua` enforces it.
- **The peaks file is in place before the length is reported**: `applyLoad` runs its `bufferChanged` as `writeSlotPeaks`'s action, after the rename has ended, and so does a playable recording's arming when it changes the slot's length (`takeArmed`, #313: the file of the new length first). The periodic `bufferState` poll repeats only what `bufferChanged` announced (`announcedBufferState`), never `bufferFrames` itself, so it never reports the arming's length before that file either (`"record: the periodic bufferState never announces an arming's length before its peaks file"`). A failed write posts `strata: cannot write <path>` and still reports the length (a waveform is a view, never a reason to hold up audio).
- The action runs only if `slotChanges[index]` is unchanged since the write began, so a load, record or clear sent meanwhile wins; or, when the caller passes `current` (a function), only while it answers true: the arming passes `slotChanges[index] == take[\change]`, which a stop that keeps the take moves along, so a K3 inside the rename never drops the new length's report.
- **A playable recording that extends its slot starts from the old overview on the new length** (#313): `startTake` reads the peak buffer and stores `shrunkPeaks` (the old bins in the first V / D of the bins, zeros after) in sclang and the buffer before the record synth is sent, because the synth's bins are over D from its first block. The overview as it was is kept with the take (`\peaksBefore`) and put back (`storeSlotPeaks`) by a cancel before it arms (`stopRecording`, and `recordSynthFreed`'s never-armed branch), since the slot then keeps its length V.
- **A refresh writes the card only for a changed overview, and at most every `peakWriteSeconds`** (#523): a playable recording's refresh (every `peakRefreshSeconds`, 0.5 s) compares what it would write (`peaksContent`: frames, rate and the 64 values as the file writes them, not the generation) with what this engine's last write of the slot's file held (`\written`, kept by `writeSlotPeaks` when the write lands, nil after one that failed) and writes nothing when they match and the file is there (`peaksUnchanged`); a changed overview is written only `peakWriteSeconds` (2 s, the record area's) after the take's last write (or its arming), in the refresh's logical time, else held for a later refresh. A loop of silence, or one whose bins have saturated, stops writing the card, and a live loop, whose bins change every pass, writes it every 2 s (about 1800 writes an hour, not 7200); the take's end, a load and an arming always write. Lua rereads a recording slot's file as often (`WAVEFORMS.refresh_seconds`, 2 s).
- **A peaks write, a save or a scratch take never forks sclang while the mover lives** (#210, #217): its rename goes to the mover through the FIFO (`renameIntoPlace`), never `unixCmd` or `systemCmd` (a fork holds sclang about 2.5 ms per 130 MB of its memory). sclang's end of the FIFO is opened `"r+e"` after the mover starts: read-write, so sclang always holds a reader and a dead mover can never SIGPIPE it (that kills sclang), and close-on-exec, so no later child holds it open and the mover ends on EOF when `free` closes it. At most `peaksMoverBacklog` (4) renames wait unacknowledged, so a write to the FIFO never blocks, even with a stuck mover. A rename the mover has not done within `peaksMoverTimeout` (1 s) goes by a subprocess, and `finish` runs once per write, with false whenever the file did not land: the mover's `mv` failed (its failure file, made before it deletes the `.part`), or the fallback's `mv` failed; the mover stays in use unless it is gone.
- `rate` is the slot's own (`bufferSampleRates[index]`), so `frames / rate` is the length the slot reports: a file at another sample rate validates in Lua.
- A failed load leaves the peaks and the file as they were; only a load that took effect stores its peaks (`storeSlotPeaks`, from the `FloatArray` its check filled). A failed server read that emptied the slot clears them, as a clear does.

## Owns

`lib/engine/StrataWaveform.sc` (`strataAreaWaveform`, order 140): the peak buffers, `\peaks` (eight 64-value `FloatArray`s, zeros until a load), `\written` (per slot, the `peaksContent` of the slot's file this engine last wrote, nil before one), `\generation` (an engine-wide count of peaks files written), `\mover` (the mover, which renames the peaks files and the files area's saves and scratch takes: `alive`, `exited`, `freed`, `pending` renames, `pid`, `file`), and:

- `peaksPath(index)`: `<settings folder>/buf<n>.peaks`.
- `storeSlotPeaks(index, peaks)`: `peaks` becomes the slot's, in sclang and the peak buffer (one `/b_setn`).
- `writeSlotPeaks(index, frames, action, current)`: writes `<path>.<instanceTag>-<generation>.part`, renames it with `mv -f` (`renameIntoPlace`), keeps what it wrote in `\written`, then runs `action` (guarded by `slotChanges`, or by `current` when given). A folder at the path fails the write (`mv -f` would move the file into it and succeed), as in `writeSlot`.
- `peaksContent(index, frames)` (the file's frames and rate lines and its values line, from sclang's overview) and `peaksUnchanged(index, frames)` (true when the slot's file is there and holds that content): the record area's refresh writes only when it is false (#523).
- `shrinkSlotPeaks(index, oldFrames, newFrames, action)`: one `/b_getn` of the slot's peak buffer; unless the slot changed meanwhile, `storeSlotPeaks` of `shrunkPeaks(values, oldFrames, newFrames)`; then `action.value(before)`, the bins as they were (a FloatArray). `shrunkPeaks`: new bin b is the largest of the old bins from `(b * newFrames) div: oldFrames` up to, not including, `((b + 1) * newFrames + oldFrames - 1) div: oldFrames` (at most 64), 0 when the first is past the last bin; integers throughout, as `spreadPeaks` (the largest product, 65 x 14.4 million frames, is under 2^31) (#313).
- `renameIntoPlace(partPath, path, finish)` (`writeSlotPeaks`, and `writeSlot` in `docs/notes/engine/files.md`): through the mover when it is alive, fewer than `peaksMoverBacklog` renames are unacknowledged and no path holds a newline: the three lines go to the FIFO (a write and a flush, 0.004-0.08 ms), then a `SystemClock` poll runs `finish` once the mover's acknowledgment is there (below). Otherwise `renameBySubprocess` (`mv -f` through `unixCmd`, the 3.3 path). A mover's failed `mv` whose `.part` is still there creates the failure file instead of the acknowledgment (`moverFailPath`: `<path>.<instanceTag>-<generation>.fail.part`, which the shell derives from the acknowledgment's name), then deletes the `.part`, so `finish` runs with false and the caller posts it (`strata: cannot write <path>` for a peaks file, `strata: cannot move <part> to <path>` for a save).
- `startPeaksMover` (in `allocState`) and `stopPeaksMover` (in `free`), below.
- `readSlotPeaks(index, usedBins, action)`: one `/b_getn` of 64 floats, the first `usedBins` spread over 64 (`spreadPeaks`, each new bin the largest of the old bins it covers, integers only), stored in `\peaks`. With `usedBins` under 64 the spread also goes back into the peak buffer (`storeSlotPeaks`), so sclang and the buffer keep one overview: a later playable recording starts from the buffer, and a 64-bin refresh reads it. A reply arriving after the slot changed stores nothing, and `action` runs either way: guarding its own steps is the caller's job (the record area's `endTake` and refreshes call it).
- `clearSlotPeaks(index)`: zeros in sclang and the peak buffer. No file: Lua draws nothing for an empty slot.

The scan itself is in `lib/engine/StrataFiles.sc` (`fileDecodes`, with its `peaks` argument): chunks of at most `loadCheckFrames` that end at bin boundaries (`peakBinEnd`, integers, every frame in exactly one bin), at most 64 more reads than the check alone. A file shorter than 64 frames fills only the bins its frames reach: the empty bins are skipped, never read.

## The file

```
strata-peaks 1
slot 3
frames 768000
rate 48000
generation 41
peaks 0.012 0.250 0.731 ... (64 values, three decimals)
```

`slot` is 1-based, like the `n` of `buf<n>.peaks`. Lua (`lib/waveforms.lua`) reads it on a `bufferState` report whose seconds changed to non-zero (forgetting the slot's old overview at the change, #401), and treats it as valid only if the header says version 1 and slot n, there are 64 values in 0-1, and `frames / rate` is within 0.01 s of the reported seconds. The mover renames in the order the writes were made, so two writes to one slot land in order. Only a rename by subprocess can finish out of order with another: with no mover, after a write's timeout, or when the mover's backlog is full (`peaksMoverBacklog` renames unacknowledged), so a write falls back while earlier ones still wait in the FIFO. Each is a few hundred bytes and a rename, so the window is milliseconds (a second, behind a timed-out rename), but an older file that lands last stays in place until the slot's next write, and Lua re-reads only when the slot's reported seconds change, so with an unchanged length the overview can stay stale. `deleteStaleParts` covers the settings folder (`stalePartDirs`), so a `.part` a crash left goes at the next alloc once older than `stalePartAge`.

## The mover

One shell per engine renames every `.part` the engine writes after alloc: the peaks files and, since #217, the files area's saves and scratch takes (`writeSlot`). A playable recording reads its peaks every `peakRefreshSeconds` (0.5 s) and rewrites its peaks file when they changed, at most every `peakWriteSeconds` (2 s, #523). Each refresh used to rename its `.part` with a `unixCmd` of its own, and `unixCmd` forks sclang: 2.2-2.7 ms at sclang's usual 130 MB, 4.5 ms at 197 MB, 9.5 ms at 394 MB (3.13, x86), plus copy-on-write faults after it, so a refresh held sclang 4-6 ms and a command from Lua arriving then waited (#210). `systemCmd` is no fix: it waits for `mv`, and on norns' glibc 2.28 it forks too. That is how a save or a scratch take renamed until #217: each held sclang for the fork and the `mv` (a 1 ms `SystemClock` task's gap across the rename: 3.49 ms median, 4.04 ms at most in the files area's check on 3.14.1, x86; after, 1.0 ms and 1.04 ms, the task's own tick).

**Where it lives.** The mover is the waveform area's (order 140): `startPeaksMover` runs in its `allocState`, after the files area's (50), and `stopPeaksMover` in its `free`. The files area needs nothing from it at alloc: `deleteStaleParts` deletes files only, and every write that renames (a save is a command, a scratch take ends a recording) comes after alloc has ended. `renameIntoPlace` reads `areaState[\waveform][\mover]` at the rename and renames by subprocess while there is none. The performance area's `writeActivePerformance` (order 10, once per alloc, before the mover starts) still renames with `systemCmd`: it must return whether the file is in place before alloc goes on, so it cannot wait for an acknowledgment, and once per alloc costs one fork.

`startPeaksMover` makes a FIFO, `<settings folder>/strata-peaks-mover.<instanceTag>.part` (`peaksMoverPath`; any old file at that name goes first, since `instanceTag` restarts with sclang), and starts one shell for the engine's life with `unixCmd` (its exit action sets `alive` false and `exited` true): `exec sh -c '<loop>' <fifo> < <fifo>`. Its loop removes the FIFO's name, then reads three lines at a time, the `.part`, the path and an acknowledgment file (`peaksAckPath`: `<path>.<instanceTag>-<generation>.ack.part`), runs `mv -f` and then creates the acknowledgment (`: >`, a shell builtin). A failed `mv` whose `.part` is still there first creates the failure file (`${ack%.ack.part}.fail.part`, `moverFailPath`), then deletes the `.part` (only if the failure file was made: otherwise the `.part` stays and the fallback's own `mv` reports truthfully); a `.part` that is gone was renamed by subprocess after a timeout, and the acknowledgment is created. Only then does sclang open its end, `File(fifo, "r+e")`; the shell's open returns once sclang's is made, and alloc waits (`peaksMoverPollStep` steps, 2 ms, at most 1 s of elapsed time: norns allocs in a `fork` that can be behind schedule, where counted waits would run back to back) until the name is gone, so no listing of the folder finds it later. The name ends in `.part` and never matches `*.peaks.*.part`, so a crash between `mkfifo` and the shell's open leaves a file `deleteStaleParts` cleans. If `mkfifo` or the open fails, or the name is still there when alloc's wait ends (a shell that never started reading), `abandonPeaksMover` posts `strata: no mover (...)`, closes sclang's end, deletes the FIFO and kills the shell, and every rename goes by subprocess at once (never a 1 s wait).

**A write through the mover** (`renameIntoPlace`) counts one rename in `pending` and polls every `peaksMoverPollStep` (2 ms). Its acknowledgment or failure file ends it: the file is deleted, `pending` drops and `finish` runs (with false for a failure file). If the mover has exited, the write renames by subprocess. After `peaksMoverTimeout` (1 s) the write renames by subprocess and `finish` runs then, once (a `finished` flag). A fallback `mv` that fails because the `.part` is gone means the mover took it first: `renameBySubprocess` asks its `partGone` function, which counts the write as written only if the mover left no failure file and the poll has not consumed one (`moverFailed`), so a slow mover whose `mv` failed is never reported as written. The rename stays in `pending`, polled every `peaksMoverSlowPollStep` (50 ms), until the mover acknowledges it, so a stuck mover fills the backlog (four renames, twelve short lines, far below a pipe's buffer, so a write to the FIFO never blocks) and later writes skip it, and one that catches up is used again. Only a mover that is gone (`peaksMoverGone`: `exited`, or no `/proc/<pid>`) stops its use; a slow or stopped one does not.

`stopPeaksMover` sets `freed`, closes sclang's end and forgets it: the mover renames what it has read, reads EOF and ends (about 10 ms). The one known limit: a poll still waiting when the engine is freed stops without running its action, so a save then never reports (its file still lands; Lua is gone by then); an acknowledgment that mover writes later is a `.part` `deleteStaleParts` cleans.

Measured after (3.13 in Docker, x86): `writeSlotPeaks`' synchronous part 0.46 ms median, 0.71 ms at most (before: 4.1-5.6 ms); during a loop recording, a 1 ms `SystemClock` task's longest gap 1.57 ms (baseline 1.12 ms; before: 4.1-5.9 ms); a message sent as a refresh starts is handled within 0.84 ms (before: 5.56 ms).
