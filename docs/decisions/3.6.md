# 3.6 decisions (integration)

The other releases: [README](README.md).

The design's twenty-one decisions, its calls and its "Cost if wrong" list are in `docs/design/3.6-design.md`. What follows was decided while it was built: by the maintainer, by the plan where the design met 3.5's merged code, and as rulings while the packages were built, reviewed and landed (the plan is removed at the release; git history keeps it). 3.6 has two series of ruling numbers that overlap: the plan's thirty-three (its section "The design against the merged code", amended at the landings) are written plan ruling N, and the build's fifty-one are written build ruling N. Code comments and notes files cite them by those names, never as a bare "ruling N". Where a later ruling changed an earlier one, both say so; a ruling marked unnumbered was taken without a number. Every device behavior below is built from the documents (the fact files under docs/design/3.6-facts/) and is unverified on the device until the 4.0 hardware check (#6).

Targets (`lib/io/targets.lua`):

- **A target may carry `layout_states`** (build ruling 11, from 2e's review): `S.register_note_target` takes them, validated as a section's, and `lib/pages/io.lua` gathers them with the voice section's as `voice: <name>`, refusing a repeated name at its start step, where `lib/io/txo.lua` had appended its states to the targets module's own section record at include (silent and order-dependent). - **A step note ends just before its gate's end** (build ruling 46, from the targets seat's second Important): on every outside target the targets core ends a step note `TARGETS.step_gap_seconds` (0.03 s, about one and a half 48 Hz steps) before its gate's end, at most half the note early; a played note is untouched. MIDI out and MPE (`lib/io/midi_out.lua`):
- **Program change in sits before the MPE branch** (plan ruling 13) of `lib/midi_in.lua`'s message handling, and the hot-plug paths keep calling `S.lib.mpe.reset_ranges()` (#688). If wrong: a program change in MPE mode is taken for a note.

- **A played note's first values are kept before its note on** (build ruling 8, from 2a's question before its first commit): `S.lib.expression.raw` was nil at a target's `note_on`, since MIDI in calls the allocator before the expression update that makes the record, so `S.lib.expression.first_touch(voice, owner, key, raw)` keeps pending values that `raw` returns until the update; MIDI in calls it after `forget` and before the play, and forgets again when the play gives no slot. Every 3.5 expression, MIDI in, MPE and notes test passed unchanged. If wrong: one small function in a 3.5 module to take out again.
- **MIDI out reads later expression itself** (build ruling 9): the note hook `expressed` fires only when a voice's mapped values change, so a pressure or slide that maps to nothing would never reach the target; MIDI out's step hook reads `raw` for each sounding played MPE note and sends what differs from that note's last send, at most `MIDI_OUT.express_per_step` (24) a step, round robin, newest values, whatever the voice's mapping, and the target has no `express` field. If wrong: at most 23 `raw()` calls a step.
- **A PSET's routes are judged together** (build ruling 19, from 2a's review): the per-param refusal turned a legal file (a swap of MPE ports) into routes it does not hold, so after a read the module's hook judges the file's routes as one set: a legal set lands exactly, whatever the lines' order, with no flash; an illegal one is placed in voice order, a voice that conflicts getting port 0, with one flash. If wrong: one hook to simplify.
- **Routes settle** (build ruling 25, replacing build ruling 19's per-param refusal outside a read): during a read the per-param actions still sent passing zone messages and several `route_changed`, so a route param's action only notes a change, and `settle` alone changes the settled routes, judging the whole set once (a changed voice's `route_changed` once; per port one takedown and one setup, for the final state only). It runs from the PSET read hook, from the LFO step when something was noted and, since #709, once at the end of `add_params`; an illegal change by hand puts back the noted route params (a bend range beside them stands) with one flash. If wrong: a hand change waits up to one step (21 ms), and tests step once between a set and its check.
- **A program change in is not echoed** (build ruling 20; built differently from its text, the code wins): one guard a port, `asked[port] = scene`, set before the recall is asked for and put back as it was when the recall is refused (an unquantized recall lands inside the call, so a guard set after a true return would come too late), replaced by a newer program change in, consumed by that scene's `scene_recalled`, untouched by other scenes' recalls. If wrong: one program change not sent if the scheduled recall never lands.
- **Every port and channel gets as many note offs as note ons** (build ruling 35; plan ruling 32; #709, Task 3e on opus): the whole-system test saw 21 ons and 1 off on one channel, because the plan's own rule for MIDI out (two ids on one note send one off, at the last) was wrong against design §3.4 and §14, and the controller's instruction to 3a ("the notes file rules") let it be written around. A note that already sounds is retriggered (an off, then the on), an id that ends while another holds the note sends nothing, the last sends the off; a step note's centered bend goes only on a member channel no other note holds; the routes settle at start. If wrong: a synth hears one re-attack where two ids meet on a note.
- **A shared member channel goes back to its notes' values when one ends** (build ruling 39, narrower than the reviewer's fix, which would make two notes on one channel resend against each other every step): on a full MPE zone, while notes share a channel the newest value written stands; when a played note there ends and others remain, each forgets what it last sent, so the step sends its current values once. If wrong: a few lines in `end_note`.
- **A note's first values on a shared channel cancel any resend pending there** (build ruling 40, splitting build ruling 39's first row, which the controller's table had missed): each other played note on the channel is taken as having sent its current values, and a later value changes nothing for them, so a legato or a re-pitch on a full zone keeps the new note's values. If wrong: the older note's value resent over the new one's.
- **MIDI out sends nothing to a port a remote holds** (build ruling 48, from the inputs seat's first Important): a port a remote grid, a remote arc or the midigrid claim holds is absent for everything MIDI out sends (notes, expression, the CC slots, program change, the MPE setup, CC 123), as `S.lib.io_remote.holds(port)` answers, and MIDI out's port rows show an owned port's owner beside its number; a controller's port is still sent to as set, the plan's own call for 2a. A remote's iii script reads notes as LED sets. If wrong: a rig whose controller port is also a synth keeps working (the plan's case); a rig that wanted notes sent to an iii device gets none.
