# 3.7 decisions (rhythm)

The other releases: [README](README.md).

The design's decisions, its calls and its "Cost if wrong" list are in `docs/design/3.7-design.md` (its "Amended 2026-11-16" block rules where the body differs). What follows was decided while it was built, as rulings while the packages were built, reviewed and landed (the plan is removed at the release; git history keeps it). Every device behavior below is built from the documents (the fact files under docs/design/3.7-facts/) and is unverified on the device until the 4.0 hardware check (#6).

The grain reader (package 1a, `lib/engine/StrataPositions.sc`):
- **A one shot goes silent only once `bufPos` + the phase is strictly past 1** (1a's review), or below 0: at exactly 1, the span's last start, it sounds, so a one shot at `bufPos` 1 with the scan at 0 sounds while it is held and a backward one shot from 1 opens at full level, with no fade-in (`oneShotLevel`, `docs/notes/engine/positions.md`). The design says so (§2.1, "past the end"; §3.5, "in one shot with the scan at 0, the note sounds while it is held"), against the plan's and 1a's brief's "at or past 1", which silenced the encoder's end stop, a bookmark at 1.000 and an LFO clamped at the top. If wrong: one comparison.

The onsets pass (`lib/engine/StrataOnsets.sc`, package 1b):
- **Each hop's energy is summed in pairs with `copySeries`, not taken from `integral`** (unnumbered, 1b's build and review): design §3.3 and its fact file (`docs/design/3.7-facts/buffers.md` §1) give `squared`, `integral`, then `copySeries` at the hop ends, but sclang's `Signal.integral` returns one Float, the whole Signal's sum, not a running sum (`prSignalIntegral`, `lang/LangPrimSource/PyrSignalPrim.cpp`, the same in 3.13.0 and 3.14.1), so there are no ends to take. `hopEnergies` squares a chunk and adds its even and odd elements eight times over, so each of a chunk's 64 sums is one hop's: C primitives only, three Signals a level, none per sample (#131), and no running total to round. The check compares it with each hop's own `copyRange(...).squared.integral` on noise. If wrong: none in what it finds; a faster primitive would change only `hopEnergies`.
- **The mean before a hop counts as at least half `onsetFloor`, and a strength is the rise in level** (unnumbered, 1b's review, the controller's ruling): the mean of the four hops before a hop is floored at half the floor so the divide after silence is finite (a hop above the floor there is a candidate, as the 2x rule would make it anyway); a candidate's strength is log2 of its ratio less 1 (the 2x threshold), then scaled so the strongest is 1. With the plain ratio, one hit after near-silence (a ratio of about 3.6e5) made every candidate inside a texture print `0.000`, so 2b's sensitivity would have been all or one; design §3.3 says "its strength is the rise". Detection is unchanged. If wrong: a strength scale that spreads the candidates too evenly, changed in `onsetChunkStrengths` alone.

The delay on the beat (package 1d, `lib/delay_sync.lua`):
- **A scene's apply ends with an open hook, `scene_applied`** (unnumbered, 1d's review, the controller's ruling): `S.lib.scenes.apply_entries` runs every `S.register_scene_applied({name, fn})` hook once, right after it clears `S.scene_recall_in_progress`, each contained. The delay holds its `setDelay` while a scene applies and its hook sends one with all four values, so a recall's send is never a mix of old and new values and never deferred (`docs/notes/lua/engine-sync.md`): an instant recall's and a fade's landing go at once; a morph's waits as every morph write does. No other seam marks the end of an apply: `scene_recalled` runs at an instant recall and a fade's first step only, and a field's own `set` cannot know it is the last. If wrong: a three-line hook removed, and the delay's recall send deferred.

The checks (Wave 1's landing):
- **A new engine area's time goes in CI's area-times comment** (unnumbered, the controller's ruling, in place of plan ruling 5): 1b's `onsets` and 1c's `envelopes` add their times there, and since #731 (1c) the structure test sums every line and checks the stated total and the "about N minutes" the docs quote, so a true table is worth more than one move at the release. If wrong: one comment line.

A file's settings (package 2d, `lib/samples.lua`):
- **A slot's binding names the audio that plays; a replace take drops the slot's own record when it ends** (unnumbered, 2d's build and two reviews, the controller's rulings): a replace take unbinds its slot when the engine stops playing the old audio (`take_started` in `lib/record.lua`, once): at the send for a take with no delay, whose slot the engine empties at once (`prepareTake`, a threshold's wait included); for a synced take at the slot's first 0 s report (the engine empties it `bufferFadeWait + recordPrepMargin`, about 0.21 s, before the start) or at its "recording" report; and a canceled take's 0 s report unbinds a slot still bound. So through a synced take's arm wait (up to a bar or more at a slow tempo) the old audio plays on with its settings, its key and its slices, and a dub into a slot a canceled take emptied never inherits the old file's settings. Plan-lua §2 put the unbind at the take's send (`recording_started`); the first review's ruling moved it to the "recording" report, which left a canceled threshold take's emptied slot bound to the old file (the second review's N1). The record goes in `confirm_buffer_audio` when the new take settles (or when it settles with no audio): a replace take canceled before the engine prepared its slot puts back the take it replaced, which then still has its settings. If wrong: the three unbind sites.
- **An unbind resends `scaleNote` and `rootNote` too** (unnumbered, 2d's build): the brief names the resend at a bind; at a clear or a replace take's start the running voices of the slot go back to 60 and the root's reference at once, so the engine's root note never lags Lua's. If wrong: one call.
- **No gain is sent while the slot records** (unnumbered, 2d's build): the peaks reader rereads a playable recording's peaks every 2 s, and a normalized file's gain sent then would boost the take while it is made, against design §4.4 ("a take is heard at its own level while it is made"; a recording of Strata's output into a boosted slot cannot feed back through the boost). The take's end rereads its peaks and sends it. If wrong: one condition in `send_gain`.

Slices (package 2b, `lib/slices.lua`, `lib/notes.lua`):
- **An overlap step's slice that does not play to its end is released at the voice's next played step** (unnumbered, 2b's build): ruling 32 has an overlap voice's step slices ring past the next step to their end, which only one shot with a moving scan has. In wrap, bounce or with the scan at 0 a slice has no end and no key to lift, so each step would add a looping slice until the cap and the pool filled. Such a slice is released at the voice's next played step and wherever the step's overrides end; a one-shot one rings on, ended by its time. If wrong: one call in `apply_step`.
- **In release mode a voice's last key leaves it running while a note of it plays to its end** (unnumbered, 2b's build): design §3.5 has a one-shot slice play to its end "whatever the key does", but release mode stops a voice at its last key (`midi_note_off_for`), which would cut it. The voice runs on and the slice ends by itself (`S.lib.notes.plays_to_end`); when its last such note ends at its time (the own note's included, 2b's review), the voice, its keys all up, stops at the next LFO step, as release mode would have stopped it. Only the held-back lift marks it, and a key down, the voice's stop and its start clear the mark (2b's second review: a mark set at every MIDI note's end stopped a voice a pattern step or K3 restarted within a step). If wrong: one condition in `end_key` and one step hook.
- **A MIDI note outside the slices is no note of that voice** (unnumbered, 2b's build): it holds no key there and releases nothing, so in release mode its lift never stops the voice, and the latch's "next chord replaces" never ends the slices that sound. A `started` for a note that plays nothing would reach the targets' hook, which would start an external note no off ends, so the note hooks gain a field of their own, `heard(voice, note, velocity)` (the controller's ruling on 2b's review), which `lib/midi_in.lua` runs for every note a voice receives, before the slice filter, and which starts nothing; the slice editor's key row listens through it. If wrong: one hook field.
- **Each slice hit restarts its scan; any other send of the own region goes only on a change; a change of the option clears it** (unnumbered, the controller's rulings on 2b's build and review, design §2 and §3.5): a played slice and a one-voice step's slice send the region every time (`set_own_region(voice, region, true)`), the same slice again included, so its scan restarts in every mode with its playhead; a sync, a recall, the option's clear and a region's end send only a change, since the engine restarts the own scan at every `regionLength`. A voice's own region set under `one` ends when `v<i>_slices` changes, so a voice turned off never keeps reading its last slice. If wrong: one flag, one action.
- **A slice note from MIDI parks** (`park = true`, unnumbered, 2b's build): the brief's MIDI note names no `park`; without it a released own slice under a held overlap slice would sound on, unheld. If wrong: one field.

Scan and follow (package 2a, `lib/scan.lua`, `lib/playheads.lua`):
- **A scan mode change restarts through `S.lib.positions.restart_scan`** (unnumbered, 2a's build): the engine's mode change never restarts its scan, so 2a sends `t_scanReset` with the mode (Wave 2's facts) through positions, which pairs it with the playhead's reset as a jump does. `lib/positions.lua` had no door for a restart alone (a jump moves `buf_pos` and, at 1, the loop), so 2a adds the function there, a few lines in 2e's file. If wrong: one function moved.
- **A voice follows only while its file has a tempo** (unnumbered, 2a's build): `S.lib.scan.following(v)` needs a buffer voice, `follow` not off and a tempo, and the bar sync and the playhead's beats read it; with `follow` on and no tempo the ratio is 1 (the brief) and nothing is synced, since there is no beat to stay on (design §2.4: "no sync ... to a voice that does not follow"). If wrong: one condition in `following`.
